# T-6.9 - Find what makes renderer-process memory grow, and fix it if it is a leak

- **Phase / depends on:** Phase 6 follow-up, after T-6.8 (main dee2feb). Owner decision 2026-11-23: attribute the growth before Phase 7.
- **Owner:** executor
- **Branch:** t-6.9

## Goal
Say with evidence which allocation grows in the renderer process during the memory session, and which user action drives it. If the growth comes from the app, fix it so that the one-hour run passes the ADR-0043 rule. If it comes from Chrome or the driver and the app cannot avoid it, show that with evidence and propose how the rule should read.

## Background
- **R-6.8 (60 minutes, headed, Iris Xe):** renderer private memory rose from 350 to 540 MB, at 3.42, 3.24 and 3.29 MB/min over minutes 4-20, 20-40 and 40-60.
  - Flat: JS heap (adjusted), external memory, the GPU process, geometries, textures, programs and DOM nodes.
  - Shards loaded stayed at 84-86 from minute 40.
- **R-6.7:** a closed path that repeats the same tiles every 100 s also grew, 359 to 398 MB over minutes 4-15. So the growth does not follow new content.
- **Not yet measured:** native allocations, split by category.

## Changes
1. **Native-memory dumps.**
   - Add an option to `web/scripts/memory-session.mjs`, for example `--dumps 600,3600`. At those times it records a memory-infra trace through CDP `Tracing` with the category `disabled-by-default-memory-infra`, requesting a detailed global dump (`Tracing.requestMemoryDump`).
   - Save a summary of the renderer process's allocator categories: partition_alloc partitions, malloc, v8, blink_gc, cc, gpu, skia, discardable, and any other present.
   - Raw traces stay outside the repo, or are gzipped and kept under 5 MB each.
   - No new dependency.
2. **What grows.** Take a short dump at about minute 10 and a later one, at least 30 minutes on: either a 40-minute run, or the hour if time allows. Compare the categories and name the ones that grow, in MB.
3. **What drives it.** Using the `--closed` path, run 10-15 minute sessions with one kind of motion at a time:
   - zoom only;
   - pan (drag) only;
   - wheel only;
   - a still camera, as a control;
   - and, if the categories point there, layer toggles or day/night switching.

   Give the renderer slope of each, and the growing category.
4. **Fix or explain.**
   - If an app path is the cause, fix it, for example a per-frame allocation that Blink or `cc` keeps, a canvas or ImageBitmap not closed, a growing typed-array pool, or a listener per frame. Then show a 60-minute run passing the ADR-0043 rule.
   - If Chrome or the GPU driver is the cause and the app cannot avoid it, give the evidence (category, the control run, and the same path in a minimal three.js page if useful). Propose a rule change in a new ADR, with the limit stated in MB/hour.
   - Do not loosen the rule without escalating.
