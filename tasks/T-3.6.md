## Goal
Make the e2e suite reliably green and add the missing visual-regression diff mechanism. Also give failed tiles one retry and a visible notice.

## Evidence (G3 review, fresh clone at ae83fbc)
- **B1.** `web/e2e/controls.spec.ts:178`, "inertia continues a fast drag after release...", failed in 4 of 12 full `npm run e2e` runs, and in 13 of 15 with `--repeat-each=15` at default workers (15/15 pass with `--workers=1`).
  - The failing assertion is `expect(rested.target).not.toEqual(atRelease.target)`, so no inertia started.
  - The cause, inferred: `releaseVelocity` in `web/src/controls.ts` counts only pointer samples in the last 100 ms (`velocityWindowMs`) and needs at least 2. Under load, `mouse.move` plus a software-GL render takes longer than that, so fewer than 2 samples remain.
- **Non-blocking 1.** No `toHaveScreenshot` assertions and no stored baselines exist, while VERIFICATION section 4 requires a screenshot diff with a stored threshold.
- **Non-blocking 2.** A failed tile is never retried, and the user gets no notice.

## Changes
1. **Deterministic inertia (B1).**
   - Use the browser event timestamps of the pointer events, not wall-clock time at processing, for the velocity window. The window then measures how the user actually moved, not how loaded the machine is.
   - Unit-test that a drag whose events carry close timestamps but are processed late still produces inertia.
   - In the e2e, make the inertia check independent of machine load. For example, dispatch pointer events with controlled timing through CDP `Input.dispatchMouseEvent`, or wait on the test state for the inertia to start and settle, polling with a timeout instead of fixed sleeps.
   - Do **not** serialise the whole suite to hide the problem.
   - Keep `velocityWindowMs` as a style/UX constant; note in the report that it must be re-checked on the Pixel 7a.
2. **Visual-regression mechanism (section 4).**
   - Add `web/e2e/visual.spec.ts` with `toHaveScreenshot` at 3 fixed fixture camera views (default, close, wide), at 1280x720 and 412x915, under `?e2e=1` (no MSAA, ADR-0027).
   - Set a stored threshold (`maxDiffPixelRatio`) in `playwright.config.ts`, starting at 0.01. Measure the actual diff between 5 repeat runs on this machine and report it.
   - Baselines live in `web/e2e/visual.spec.ts-snapshots/`. Generate them now as **candidate** baselines from the fixture, and commit them with a README line saying the owner approved them on the date the orchestrator records. Leave the date as `PENDING` in the README; the orchestrator fills it in after the checkpoint.
   - CI runs on Linux, so the baselines are platform-specific. Configure `snapshotPathTemplate` to include the platform. Generate the win32 baselines here, and make the Linux ones a documented `--update-snapshots` step for the orchestrator. Never let a missing baseline pass silently in CI: in CI, mark the visual test as skipped with an explicit reason until the Linux baselines are committed.
3. **Tile retry and notice.**
   - Retry a failed tile once after 2 s.
   - If it fails again, show a small non-blocking notice through i18n ("Some map areas could not be loaded" / "Alcune zone della mappa non sono state caricate"), dismissible, and not covering the attribution.
   - Keep exactly one console error per finally-failed tile.
   - Unit-test the retry with a fake loader; e2e with a 404 route checks for the notice.
