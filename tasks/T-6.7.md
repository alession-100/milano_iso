# T-6.7 - A stronger memory pass rule: sample every zoom phase, include process memory, bound the catalogue

- **Phase / depends on:** Phase 6 follow-up, after G6 PASS WITH RISKS (main 3097949). Closes the first G6 review's N1, which was carried as a Phase 6 risk.
- **Owner:** executor
- **Branch:** t-6.7

## Goal
The memory session (`npm run memory`, T-6.4) would catch a real leak. Reaching its pass rule should mean that memory stays bounded over long use, not only that the JS heap medians of two minutes agree.

## Background (first G6 review, N1)
- **Sampling.** Samples come every 10 s, which divides the 50 s zoom period, so they always land on the same 5 zoom phases: about 250, 650, 3,060 and 3,085 m. The 4,000 m phase is never sampled.
- **Orphan check.** It allows 37 geometries and 64 textures of slack, because `renderer.info` counts only uploaded geometry.
- **What the heap leaves out.** The heap figure excludes ArrayBuffers and GPU memory, and process memory is not checked.
- **Shard catalogue.** It is kept by design: 7.5 MB with 4 of 101 shards loaded, 12.4 MB with 88. It explains the heap creep.
- **12-minute run.** It fails the script's own rule (heap +12.4 %; minute medians 11.80, 11.98, 11.85, 12.59, 12.42, 13.03 MB). Over the same run, renderer process private memory grows: about 280 MB in minute 2, about 375 MB at minutes 4-5, and 400-457 MB at minutes 10-12. The GPU process stays flat at about 260-390 MB.
- **Recent runs.** Heap +1.39 % (first review), +7.74 % (second), +2.31 % (third).
- **Evidence:** `C:\Users\studi\AppData\Local\Temp\g6rev\` (`mem1.json`, `mem2.json`, `procmem1.csv`, `procmem2.csv`, scripts), read-only.

## Changes
1. **Sampling.** Use a period that does not divide the zoom period (for example 7 s or 13 s), or sample at fixed zoom phases, so that every phase from 60 to 4,000 m is sampled, including 4,000 m. State the phases covered.
2. **What is measured.** Add:
   - **ArrayBuffer and external memory** (for example CDP `Runtime.getHeapUsage`, `Performance.getMetrics`, or `performance.measureUserAgentSpecificMemory` if available without new headers);
   - **renderer process memory** (for example Chrome's own process metrics through CDP, or an OS sampler of the renderer PID; say which and how portable it is);
   - **a tighter orphan check:** count the geometries and textures the app itself holds against `renderer.info`, so that slack is explained rather than allowed.
3. **The catalogue.** Either bound the shard catalogue (for example evict shards not needed for some time, with a test that evicted shards reload correctly) or keep it and make the rule account for it explicitly, with its maximum size measured with every shard loaded. Choose by measurement and state it in the ADR.
4. **The rule.** It is stated in the ADR and in the script. Proposal, adjust with reasons:
   - after warm-up, heap (excluding the catalogue, if kept), external memory and renderer process memory each have a last-period median within a stated percentage of an early-period median, or a fitted slope under a stated MB per minute;
   - geometries and textures never exceed what the cache limit allows;
   - DOM nodes are constant.
5. **Long runs.** Run the session for 5 minutes (the G6 criterion) and for at least 20 minutes, headed, on the real GPU.
   - If renderer process memory still grows, find out whether it plateaus (allocator, GPU-side caches, decoded glb buffers) or keeps climbing. Attribute it, with a heap snapshot comparison or CDP `Memory` counters if needed.
   - Fix a real leak if you find one. Otherwise explain the growth with evidence.
6. **Payload script.** Fix the header of `web/scripts/measure-payload.mjs`, which says "3 MB = 3,145,728 B", to the VERIFICATION reading of 3,000,000 B. Check its pass check uses the same number.
