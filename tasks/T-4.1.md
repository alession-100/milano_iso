# T-4.1 - Trees (OSM-mapped plus a labelled seeded fill) and road markings, pipeline to screen

- **Phase / depends on:** Phase 4 / ADR-0028. Runs in parallel with T-4.3.
- **Owner:** executor

## Goal
Add trees and road markings to the pilot. Mapped trees are data; fill trees and markings are style, and every stylised item is flagged as such in the tile feature tables.

## Changes
1. **Mapped trees (data).**
   - Extract OSM `natural=tree` nodes and `natural=tree_row` ways inside the processed extent into a new processed layer `trees` (EPSG:32632).
   - A `tree_row` is mapped as a line. Place trees along it at a style-constant spacing; those positions are style, the line is data.
   - Fields: `osm_type`, `osm_id`, `source` (`osm_tree` | `osm_tree_row` | `fill`), `decorative` (false for both OSM sources), `height_m`, `height_source` (`osm_height` when the tag is a parseable number, else `style_default`).
   - Log the counts and the drops (unparseable tags, outside extent) like the other layers.
2. **Decorative fill (style).**
   - Inside green areas whose `kind` is a park or garden type, add fill trees on a jittered grid. Use a fixed seed, sorted iteration and a style-constant density.
   - Keep each fill tree at least a style-constant clearance from buildings, roads, road areas, water and mapped trees.
   - Fill trees have `source=fill`, `decorative=true`, no OSM id, and `height_source=style_default`.
   - The fill must be deterministic: same inputs give identical output.
3. **Road markings (style, placed on data).**
   - Add a flat layer `markings`:
     - dashed centre lines on the road classes listed in a style table;
     - zebra crossings, only where OSM maps a crossing (`footway=crossing` ways, or `highway=crossing` nodes on a road, whichever the extract supports; report which).
   - Every marking row carries `stylised=true` and the `osm_id` of the road or crossing it comes from.
   - Use the existing `LAYER_HEIGHT_M` ordering to prevent z-fighting: markings sit just above roads.
4. **Tiles.**
   - Export trees so the client can draw all the trees of a tile in **one draw call**: an `InstancedMesh` per tile, from per-tile instance data in the glb or in the feature table JSON. Choose one and justify it in the report.
   - Feature tables expose every tree's fields above. Update `tiles.schema.json` and the manifest layer list.
   - Byte-identical rebuilds still hold. Each tile stays <= 250 KB gzip; report the new maximum.
5. **Client.**
   - Render trees as low-poly instanced shapes (for example a cone or icosahedron crown and a short trunk), with style-constant colours added to `web/src/style/palette.ts`.
   - Scale trees by `height_m`.
   - Markings use one material through the existing per-tile layer mechanism (ADR-0026).
   - The palette limit is 32 (ADR-0029); set `MAX_PALETTE_COLOURS` to 32 if T-4.3 has not already. Append new entries after the existing ones; never reorder or recolour palette v1 entries.
6. **Fixture.**
   - Extend the synthetic fixture with:
     - a few mapped trees;
     - one tree_row;
     - one park that receives fill trees;
     - one road with markings;
     - one crossing.
   - Regenerate it through the real exporter; the byte-identical test must still pass.
   - Update the expected counts in the specs and regenerate the win32 visual baselines (delete the old ones first, see the snapshots README). Leave the `*-linux.png` files untouched: the orchestrator handles them.
7. **Data checks** (`tests/data`, marker `data`):
   - counts of mapped and fill trees;
   - no fill tree inside a building footprint or on a road;
   - every fill tree carries `decorative=true`;
   - the fill is deterministic across two runs.
