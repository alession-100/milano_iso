# T-5.3a - Search index and minimap data (pipeline)

- **Phase / depends on:** Phase 5 / G4 passed. Runs in parallel with T-5.2.
- **Owner:** executor
- **Branch:** t-5.3a

## Goal
Produce two static files next to the tiles, for the client UI that T-5.1 and T-5.3b build later:
- a **local search index** of named features, so search needs no third-party API (CLAUDE.md: no runtime calls to map APIs);
- a small **minimap** drawing of the whole tileset extent.

- Real data: copy (or hardlink) `C:/Users/studi/Documents/milano-iso/data` into `data_t53a/` in your worktree, set `MILANO_ISO_DATA` to it, and run `make data` once. The shared cache predates Phase 4. Never write into the shared cache.

## Changes
1. **`index.json`** (written by the tile export, listed in the manifest).
   - Entries:
     - named buildings, with `name` from the data;
     - named streets: roads grouped by exact name, one entry per name, with the union bbox and the list of `osm_id`s;
     - named green and water areas;
     - landmarks, with their `name` from `tests/landmarks.yaml`.
   - A landmark's entry name takes precedence over a building name transferred to the same feature. This fixes the "Palazzo Carminati" / Generali mix-up in PROGRESS (G1 carry-over 2).
   - Only rendered, above-ground features with a non-empty name. Never include fill trees, markings or landmark details.
   - Each entry: `name`, `kind` (`building` | `street` | `green` | `water` | `landmark`), `centre` (local x, z in metres, rounded to 0.1 m), `bbox` (local, rounded to 0.1 m), `tiles` (tile names it touches), and `ref` (how to find the feature: building `key`, or `osm_type` + `osm_id`, or `landmark_id`).
   - Names exactly as in the source (ADR-0006: no translation). Do not pre-fold accents: the client folds them.
   - Sort deterministically: by kind order, then name, then ref.
2. **`minimap.svg`** (written by the tile export, listed in the manifest).
   - It covers the full content extent in the local frame, with an explicit `viewBox` in metres, north up.
   - It shows water, green areas, the building union and major roads, each simplified with a tolerance that keeps the file <= 100 KB gzip for the pilot (report the tolerance, and estimate the whole-city size for Phase 6).
   - Layer colours come from CSS classes, not inline colours, so the client can theme them for day and night.
   - Snap every coordinate to 0.1 m and sort paths deterministically, so the file is byte-identical on Linux and Windows (see Lessons learned and T-4.4).
3. **Manifest and schema.**
   - Add `index` and `minimap` (relative file names, with sha256 and gzip size) to `tiles.json`, and update `tiles.schema.json`.
   - The client manifest parser must accept and expose them, keeping the existing validation.
4. **Fixture.**
   - Give the fixture a few names: a street made of 2 ways with the same name, a named park, and the landmark.
   - Regenerate the fixture through the real exporter. The byte-identical test must cover the 2 new files.
5. **Tests.**
   - pytest (synthetic):
     - grouping streets by name;
     - landmark name precedence;
     - stylised and decorative features excluded;
     - sort order;
     - SVG well-formed (parse with the standard library) and viewBox correct;
     - determinism under ±1e-9 m input shifts, as in T-4.4.
   - `tests/data` (real pilot):
     - every in-pilot landmark of `landmarks.yaml` has an entry;
     - the Duomo entry centre lies within 5 m of its `landmarks.yaml` position (local frame);
     - entry counts by kind reported.
