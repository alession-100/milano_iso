## Deviations and assumptions
- Root cause finding: `controls.ts` already used `e.timeStamp` of the pointer events (not wall-clock), so no production change was needed for B1. The flakiness came from the test: Playwright `mouse.move` plus 10 ms waits get genuinely spread out by load, so the real event timestamps were more than 100 ms apart. The fix is therefore in the e2e (explicit CDP timestamps); Chromium honours the `timestamp` parameter in headless (20/20 and 10 full runs green, so no escalation needed).
- `velocityWindowMs` (100 ms) is unchanged. It is a UX constant and must be re-checked on the Pixel 7a.
- The 404 e2e filters out the browser's own "Failed to load resource" console lines when counting errors (they are emitted per HTTP attempt by Chromium, not by the app) and asserts exactly one app error per finally-failed tile. Whether Chromium emitted them in this run was not examined.
- A retrying tile counts as `loading` in stats (so `loading` is non-zero up to 2 s after a failure).
- Notice styling is inline in `main.ts` (index.html outside the card's file scope).
- The visual spec waits for `loading === 0 && loaded >= visible` and two animation frames; the "default" view is target (0,0) width 600 m, close 150 m, wide 1200 m.
- Baseline README leaves the approval date as `PENDING`, as specified.
