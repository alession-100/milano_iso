## Manifest design (ADR-0038 point 1)
`tiles.json` is a small root (header, attribution, layers, `levels`, `index`, `minimap`, `totals`, `bounds_local`, `shards`). A shard `shards/S<level>_<a>_<b>.json` holds the unchanged tile entries of one level in one square of 8 x block (2, 4, 8, 16 km); the root lists each shard with its size, sha256, tile count and content box. The client fetches the root, then the shards of the level in use that meet the view. City: root **29,240 B** raw / 9,331 gzip-9 / **7,318 B** brotli served (was 2,364,416 / 674,597); 101 shards (68 / 21 / 8 / 4 per level, 2.37 MB raw in all, largest 39,618 B raw with 72 tiles). Pilot: root 7,222 B, 16 shards.

## Cache rules (ADR-0038 point 2)
| file | Cache-Control | why |
|---|---|---|
| `index.html`, `/` | `no-cache` | names the hashed JS |
| `tiles/<extent>/tiles.json` | `no-cache` (and the client uses `cache: 'no-cache'`) | the only manifest file that is not content-addressed |
| `/assets/*` (Vite, content hash) | `public, max-age=31536000, immutable` | the name is the hash |
| tile `.glb`/`.json`, `shards/*`, `index.json`, `minimap.svg` requested as `?v=<sha256[:12]>` | `public, max-age=31536000, immutable` (without `?v`: `no-cache`) | the URL changes with the content |

`Content-Encoding` br first, then gzip; `Vary: Accept-Encoding`; ETag per encoding, 304 on revalidation. `public/_headers` says the same for `Netlify`/`Cloudflare Pages` style hosts (not tried, not deployed; GitHub Pages does not read it).

## Budget results the orchestrator must decide on
1. **Gzip-only client on a phone: 4.44 to 4.63 MB against 3 MB.** `VERIFICATION.md` 5 says "Initial payload (gzip/brotli) <= 3 MB"; I read it as "with whichever the client gets". Every browser asks for br, but a host that serves gzip only (GitHub Pages, to be confirmed) would put the 412x915 default view (level 1, 2.15 MB of tiles with br, 4.25 MB with gzip) over the budget. I did not change anything to hide this. Options: require brotli from the host; or shrink the level 1 tiles in the default phone view (T-6.2 territory); or accept 1280x720 only for gzip hosts.
2. **The prefetch ring.** I count the payload "until the default view is complete" up to the arrival of the last tile in view (the ring is fetched after the tiles in view). If the ring is counted too, the phone with brotli is at 3,154,866 B: 0.3 % above 3 MiB (3,145,728) and 5.2 % above 3,000,000. The ring is one 250 m tile ring around the view; reducing it at level 1 and above would fix this but is a streaming-policy change I did not make.

## Deviations and assumptions
1. **`tiles.json` is now the root, format 2** (the client refuses 1; the old full manifest is rebuilt by `load_full`). Card allowed "per-level or per-block manifests"; I chose per level and area. All pytest/vitest/e2e that read the manifest were changed to read root + shards. The plain and lod fixtures are regenerated (their tile files are byte-identical; `tiles.json` changed, `shards/` added) - the card said the pilot base tiles stay byte-identical, which holds; the fixtures' `tiles.json` is not a base tile.
2. **Version query instead of revalidation** for tile files (ADR point 2; the card left the choice to the ADR). `tiles.json` is fetched with `cache: 'no-cache'`.
3. **Tiles in view are requested before the prefetch ring** (`lod.ts`): not in the card in these words ("a good order"); without it the default phone view fetched its ring first and the payload was 3.16 MB at the moment of completion. Nearest-first within each group is kept.
4. **Precompression** runs on `web/dist` (which contains `public/tiles/<extent>`); I compressed the 340 MB once and copied the `.br`/`.gz` back into `web/public/tiles/city`, so a build copies them and `precompress` keeps a variant that already decodes to the file. The card's "and `web/public/tiles/<extent>`" is covered by passing that directory to `scripts/precompress.mjs`; I did not make `build` do it (13 min at quality 11).
5. **The gzip OS byte is set to 255** to be platform independent; the compressed bytes can still differ between Node builds/CPUs (not claimed otherwise).
6. **Measurement method (mine):** "view loaded" cut at the arrival of the last tile in view, bytes mapped from CDP timestamps to the page clock; one fresh warmed-up browser per run. My first full run reused one browser for all runs and showed two 35 to 38 s stalls of the animation frame in the first 412x915 run after a heavy desktop path run (a GPU-process effect, not the app: view loaded was 1.0 s in the same run); I replaced the whole data set with runs in fresh browsers. Only the final data is in the artifact.
7. **Chromium throttling** applies to the connection; the local server adds no latency of its own.
8. **Tests changed to match the new behaviour:** `lod.spec.ts` "a coarse block stays until the base tile..." now waits for the three base tiles before the level changes (a tile in flight when its level is replaced is cancelled by design); `tiles.spec.ts` "unexpected format" sends format 1; route patterns of eight specs got a `*` for the `?v=` query; `rotation`/`picking` unchanged.
9. The older evidence scripts `measure-lod.mjs` and `measure-contrast.mjs` read the manifest; I changed them to read the shards but did not run them.
10. A stray background process of mine (the first city build, started with the old manifest code) was left to finish because the guard denied terminating it; it only wrote `data/tiles/city`, which was rebuilt afterwards. Servers and the measurement run were stopped by port; five of my own shell processes whose command line contained the port were stopped with them.
11. `docs/PROGRESS.md` not edited (the orchestrator's); ADR-0038 is `Proposed`.
