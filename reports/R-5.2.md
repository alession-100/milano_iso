## Deviations and assumptions
1. **Culling and shadow fit needed no change.** Both derive from the camera frustum and view footprint, which are azimuth independent. The test the card asks for (every tile that has a ground point in view is in `visible`, 12 views over 4 azimuths; shadow frustum contains the footprint and casters at each step) found no bug, so no fix was made. Not a "tests first, then fix" case.
2. **Direction convention (assumption).** Q = city turns counter-clockwise on screen = azimuth +90 (45 -> 135); E = clockwise = azimuth -90 (45 -> 315). The card names only "counter-clockwise" and "clockwise" for Q and E. "Rotate left" = Q, "Rotate right" = E.
3. **Visual baselines hide the buttons.** The new buttons would have changed all 24 existing baselines (including the `linux` ones, which I may not regenerate). `visual.spec.ts` therefore passes `stylePath: e2e/visual-hide-controls.css` (`#rotation-controls{visibility:hidden}`, layout unchanged) so existing baselines stay valid and the look remains the approved one (ADR-0030). The buttons are tested in `rotation.spec.ts` only, not by screenshot. If the orchestrator prefers the buttons in the baselines, remove the stylePath and regenerate all win32 and linux PNGs.
4. **Linux baselines for the 3 new views x 2 sizes are missing** (`default-rot{1,2,3}-*-linux.png`), as the card says to leave them. The CI visual job will fail on them until the `visual-baselines` workflow is run.
5. **Reset key `0`** resets target and zoom but not the azimuth (the card did not say). Rotation is a separate user choice.
6. **Rapid presses** use the "snap to end state, then animate the next" option; none are queued.
7. Debug readout got an `az` field (small addition so readouts show the view). Debug overlay (top left, up to 380 px) can overlap the buttons on a 412 px phone only when `?debug` is on; not checked by a test.
8. The card's verification line `make setup` was run first; `make web-tiles` was run with the given data dir and the copied tiles removed afterwards.
9. `window.__milanoIso.camera.azimuthDeg` is an intermediate value during an animation, exact only at rest.

## Amendment: flaky tile test (reviewer finding)
- Cause confirmed: a test race, not an app bug. `tiles.visible` is only updated by a render (render-on-demand), so right after `setView` or a key press it still reads its old value (0 at start) until the next animation frame. `settle()` passed trivially (`loaded + failed >= 0`) and the test then read `visible` = 0. The app reports the correct value one frame later.
- Fix (test only): the test now polls one state object until step, azimuth, `visible`, `loaded`, `loading` and `failed` all equal the expected values (20 s timeout, no fixed sleeps); `settle()` also requires `visible > 0`.
- Proof: `npx playwright test e2e/rotation.spec.ts --repeat-each=20` at default workers: 160 passed (1.4m). Full e2e, 3 consecutive runs: 54 passed each. Lint and typecheck clean.
