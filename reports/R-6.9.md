# R-6.9 - What makes renderer-process memory grow

- **Status (updated after the owner's follow-up):** a 60-minute no-driver run with workload counters is flat (renderer -0.10 MB/min in minutes 40-60, 269 MB median), while a back-to-back 20-minute Playwright run grows 4.4 MB/min; tile requests match within 2 %, frames differ by 16 % (not within 10 %, see section 3). The first no-driver run was invalid (hidden tab) and is withdrawn.
- **Status:** PARTIAL - escalation, outcome (b). The growth is not an app allocation: it exists only when the Playwright driver is attached. The card's "Escalate if" condition 1 applies (growing category inside Chrome or the driver, no app change affects it). No app fix was made; ADR-0044 is **proposed** in `docs/DECISIONS.md` and nothing in the rule was loosened.
- **Branch / commits:** `t-6.9` from main ca0b020.

## What changed
- `web/scripts/memory-session.mjs`: `--dumps 600,2400` (memory-infra dump through CDP `Tracing`, category `disabled-by-default-memory-infra`, `Tracing.requestMemoryDump` detailed; summary of the renderer's allocators to `<out>.dump<s>.json`, raw trace gzipped into `--dump-dir`), `--dump-dir`, `--motion full|path|zoom|pan|wheel|drag|still`. Default behaviour (`full`, no dumps) unchanged.
- `web/scripts/memory-dump-compare.mjs` (new): compares two dump summaries, prints allocator categories and changes in MB.
- `web/scripts/memory-nodriver.mjs` (new): the same closed camera path with no automation driver (Chrome started by the script, raw CDP only for `Target.createTarget`, `Runtime.evaluate`, browser-level `SystemInfo` and `Tracing`). Windows sampler.
- `docs/DECISIONS.md` ADR-0044 (proposed), `docs/PROGRESS.md` T-6.9 row, `reports/artifacts/T-6.9/`.
- No app (`web/src`), pipeline, dependency, baseline or threshold change. Raw traces (8 to 10 MB each) stayed outside the repo.

## Setup
Own `npm ci` and `vite build` in `web/`, tiles copied from `t66data/dist1/tiles` (read-only). Served on 4213 (my process, killed at the end). Headed Chrome (channel chrome), one run at a time. 4173 and 4174 untouched. Metrics are the page's `private_footprint_bytes` from memory-infra (the renderer with a `webgl` allocator) and the OS renderer sum used by the session (all renderer processes, including two small helper renderers of about 60 MB together).

The growing category is Blink's own garbage-collected heap. Named objects in it: `blink::NetworkResourcesData::ResourceData` 3.6 to 14.0 MB (+10.4) and its hash table backing, which is the DevTools network agent's per-request record. Those named objects are about 12 MB of the 83 MB; the rest of `NormalPageSpace3` is heap pages whose contents the dump does not name, so I state that the growth is in the Blink GC heap and that the network agent record is **present and growing**, not that it accounts for all of it. `partition_alloc` is about 220 MB in every driver run (its `buffer` partition 215 MB) and about 10 to 25 MB without the driver (see 3), so the large steady block is also driver-linked.

- Still and wheel are flat and load no tiles beyond the first (shards 4 to 4; the wheel does not move the camera enough to load more). Zoom and pan, which keep requesting tiles, grow at about 1.6 to 1.8 MB/min by minute 7 and still climb; drag fills the same 220 MB `partition_alloc` block more slowly (a warm-up, not yet at a steady slope after 10 minutes), so a 10-minute run is too short for it. - In every run the driver-side block `partition_alloc` reaches about 220 to 230 MB once tiles flow, then `blink_gc` keeps rising.

### 3. Control: same closed path, no driver, with a matched workload (second attempt; the first was invalid)
**The first no-driver run (`superseded_*` files) is withdrawn.** It recorded only memory, and when the coordinator asked for proof that the page did the same work, a smoke test of the same script showed the new window going `hidden` with focus lost after 14 s and the frame counter freezing (1,650 frames at t=14 s and still 1,650 at t=28 s): Chrome backgrounded an occluded window, so the flat 59 MB footprint of that run was a throttled tab, not evidence. Fix: `memory-nodriver.mjs` now opens the page with `newWindow: true`, calls `Target.activateTarget`, and starts Chrome with the flags Playwright uses (`--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`, `--disable-background-timer-throttling`, `--disable-features=CalculateNativeWinOcclusion`). Each sample reads, through `Runtime.evaluate` and `Runtime.getHeapUsage` only (no Network, Page or DOM domain enabled): `document.visibilityState`, `document.hasFocus()`, a requestAnimationFrame counter installed by the script (`window.__memFrames`), `tiles.started` (cumulative tile requests of the app's own counter), tiles loaded and in scene, shards, level, width, geometries, textures, programs, JS heap. The Playwright runs record the same fields (added to `memory-session.mjs`).

Runs, headed, one at a time, back to back, same closed path: no driver 3,600 s (dumps at 600 and 3,590 s), Playwright `--motion path` 1,200 s (dumps at 600 and 1,190 s). Files: `nodriver2_closed_60min.{json,log}`, `playwright2_path_closed_20min.{json,log}`, `workload_compare.{mjs,txt}`, `dump_compare_nodriver2_600_vs_3590.md`, `dump_compare_playwright2_600_vs_1190.md`.

**Visibility.** All 171 samples of the first 20 minutes (and all 514 of the hour) read `visible` in the no-driver run, and frames advanced at about 120 per second throughout. `hasFocus` was true early and false for the rest (another window had focus, the owner's desktop); visible with advancing rAF is the condition that matters, and it held. ## Deviations and assumptions
- Outcome (b) reached, so there was no fix. Follow-up (owner decision, section 3): a 60-minute no-driver run and a back-to-back 20-minute Playwright run with workload counters were done; the first no-driver run was invalid (hidden tab) and is kept as `superseded_*`.
- Workload match: tile requests, shards, levels and geometries/textures match within 2 %, but frames per minute differ by 16 % (no driver higher), outside the 10 % asked for. I therefore state the attribution as strongly supported, not as a strictly matched proof.
- The no-driver run reads JS heap without a forced GC (Playwright runs force one), so heap values are not comparable between the two; the forced GC itself was not applied to the no-driver run because it needs the HeapProfiler domain.
- "Visible foreground": the window is created with `newWindow: true` and `Target.activateTarget`, Chrome gets Playwright's anti-backgrounding flags, and every sample records `visibilityState` (all `visible`) and a growing rAF counter. Window focus was lost to another application part of the way (`hasFocus` false in 86 of 171 samples of the first 20 minutes), the window itself stayed visible and drawing.
- The mid-run tile fetch count is the app's `tiles.started` counter, not `performance` resource entries (capped at 250 by the browser).
- The scripts were edited after the first commit (counters, flags): `git diff 2acdfbd` shows it.
- Motion runs are 620 s, not the 10 to 15 minutes at the longer end; drag had not reached a steady slope.
- `--motion path` (scripted path, no real input) and `memory-nodriver.mjs` are additions beyond the card's wording, needed for the control.
- The dumps are taken after the sample of the interval and take a few seconds each; sampling is delayed slightly then. The tracing is on only during a dump.
- The page renderer is picked by having a `webgl` allocator; the session's OS sum also counts two small helper renderers. Windows `PrivateMemorySize64` and memory-infra `private_footprint_bytes` differ by definition, so only changes within one measure are compared.
- I did not isolate the exact Chrome component (whether DevTools `Network` agent buffering or another Playwright agent). Direct proof would be a Playwright session whose network agent is off, which the driver does not offer.
- 12 MB of raw dump summaries are committed (16 small JSON, about 0.65 MB each); raw traces (gzipped 0.8 MB each) are outside the repo.
- The vite build at the end emptied my `web/dist` (including the copied tiles); it is gitignored and unused after the runs.

## Open questions and risks
- **Decision for the orchestrator:** adopt ADR-0044 (renderer rule judged by `memory-nodriver.mjs`, driver-attached figure informational with a 250 MB/hour ceiling). The 60-minute no-driver run it needed is done (-0.10 MB/min in minutes 40-60); the caveat is the 16 % frame-count difference. Until it is adopted `npm run memory` still fails the renderer rule on any run over about 8 minutes (3.3 to 3.9 MB/min against the 6 MB/min slope and the +20 % change).
- A real user without devtools should not see this growth, but the one-hour no-driver run is a scripted path, not a real user session, but it covers tile eviction and reloading (14,000 tile requests per 20 minutes).
- The same driver cost would apply to the e2e and bench runs (renderer memory only; fps not shown to be affected).
