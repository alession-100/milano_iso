## What changed
- `pipeline/milano_iso/classify.py` (new): OSM tag rules as a `RULES` table of `Rule` records (layer, geometry kinds, key, values, exclusions, `when`/`unless`), plus `classify()`, `highway_class()`, `is_underground()`, `top_tag_key()`, `named_category()`.
- `pipeline/milano_iso/normalise.py` (new): `python -m milano_iso.normalise --extent pilot`. Reprojects (pyproj, `always_xy=True`), repairs/drops/deduplicates, writes `processed/pilot.gpkg`, `processed/drop_log.csv` and the artefacts.
- `pipeline/milano_iso/dbt_extract.py`: also extracts `EDI_MIN_CR_EDF_IS` (`edi_min`), `EDI_MIN_CR_EDF_ME` (`edi_min_me`) and the attribute tables `EDIFC.dbf` (`edifc_attr`), `EDIFC_EDIFC_USO.dbf` (`edifc_uso`), `EDI_MIN.dbf` (`edi_min_attr`), keyed by `CLASSID`/`CLASSREF`. The canonical-dump function moved out.
- `pipeline/milano_iso/geo.py`: now holds the shared `canonical_dump_sha256` (re-imported by `dbt_extract`, so `ex.canonical_dump_sha256` still works; used by `normalise`).
- `pipeline/milano_iso/dbt_fetch.py`: uses `milano_iso.fetch.fetch` instead of its own download/hash code. `SOURCES`, `target_path`, `manifest_path`, expected-size check kept.
- `pipeline/mk/30-normalise.mk` (new): target `data-normalise` (depends on `data-boundary data-osm data-dbt`), appended to `DATA_STEPS`.
- `tests/pipeline/test_classify.py`, `tests/pipeline/test_normalise.py` (new, synthetic data only); `tests/pipeline/test_dbt_extract.py` (the dbt_fetch test adapted to the shared helper).
- `reports/artifacts/T-1.3/`: `validation.md`, `validation.json`, `drop_log.csv`, `transform.md`.
- `reports/artifacts/T-1.2/summary.json`: regenerated by `make data` (new layers in `counts` and `sort_keys`; the canonical sha of `dbt_pilot.gpkg` changed from `f71400ef...` to `793eb005...` because the file now has more layers). No other T-1.2 content changed.

## Deviations and assumptions
1. **`osm_type` column added to every OSM layer** (the card lists only `osm_id` for roads, rail, water, green, landuse, road_areas). OSM ids are unique only per type, and the dedupe key is `(osm_type, osm_id, geometry)`.
2. **Extra `underground` boolean column** on `osm_buildings`, `osm_building_parts`, `roads`, `road_areas`, `rail`, `water`, `dbt_volumes` (the card says "flag them `underground=true`" without naming the column). `tunnel=building_passage` is not flagged (rule is `tunnel=yes`). For a multi-valued `layer` (`-1;0`) the flag is set only if all values are negative. `tunnel=culvert` is not flagged.
3. **DBT underground:** `UN_VOL_POR` = `08` ("sotterranea", spec p.134) is flagged. The pilot has none (counts in `validation.json`).
4. **`named_features` for lines and areas** uses `point_on_surface` of the geometry clipped to the pilot box (not of the whole feature), so that every label point lies inside the extent (extent assertion). For features that cross the box edge this differs from the representative point of the whole feature. Points are kept as is.
5. **Roads from areas:** an OSM area with `highway=*` and `area` not `yes` becomes its boundary line in `roads` (as the card says); this includes the 29 areas the OSM extract assembled from closed highway ways (all pedestrian/footway; no roundabout appears as an area in the pilot). Closed roundabouts that stayed line geometry are in `roads` as they are.
6. **`class` normalisation:** `*_link` maps to the base class; classes not in the list in `classify.py` map to `other`. The pilot output has no `other`.
7. **Classification table choices** (not given by the card, they are mine and live in `classify.py`): green = leisure {park, garden, playground, pitch, recreation_ground, nature_reserve, golf_course, dog_park, common}, landuse {grass, forest, meadow, flowerbed, orchard, vineyard, cemetery, village_green, recreation_ground, allotments, plant_nursery}, natural {wood, scrub, grassland, heath}, amenity=grave_yard. `water=*` on an area (for example `reflecting_pool`) is water even without `natural=water`. Waterway lines: every `waterway=*` value. The orchestrator may want to review these lists.
8. **Labels:** `type_label`/`status_label` come from the spec (EDIFC_TY pp.135-137, EDIFC_STAT p.141, EDI_MIN_TY pp.151-152, EDI_MIN_ST p.152; page numbers from the printed footers; text read with `pdftotext`). EDIFC_USO is kept as codes only (`use_codes`, multi-valued, joined with `;`): the PDF table layout (pp.136-141) does not extract reliably, so I did not guess labels. 
9. **`dbt_buildings`** has 217 rows = 170 EDIFC_CR_EDF_IS + 47 EDI_MIN_CR_EDF_IS footprints; one EDIFC building (of 171 in `edifc_me`) has no ground footprint record (known from T-1.2) and is therefore absent. `building_class` of a volume is decided by membership of `CEDIUV` in `EDIFC.CLASSID` / `EDI_MIN.CLASSID` (attribute tables extracted for the buildings in the pilot footprints and the `CEDIUV` of pilot volumes).
10. **`av_m` and `qe_m`** are stored as in the source; metres is the T-1.2 inference, not a spec statement. `base_z_min_m` / `base_z_max_m` are min/max Z of the exterior ring(s) (as T-1.2 `base_z`); the Z vertical datum is NOT IN SPEC.
11. **Layer geometry types:** osmium produces MultiPolygon for all OSM areas, so the OSM polygon layers are MultiPolygon and `roads` is MultiLineString (GeoPackage promotion when mixed). No simplification or type change is applied otherwise.
12. **`dbt_fetch` refactor:** log line wording changed (`dbt2020: skip, sha256 ok (...)` instead of `skip download (sha256 matches manifest)`; it now goes through `logging`, set up in `main`). Fetch errors still exit via `sys.exit`. Manifests newly written by the shared helper would carry extra keys `source` and `file`; the existing committed manifests are untouched. The expected-size check is applied only after a fresh download, as before, and removes the new manifest if it fails. The old dbt_fetch unit test was rewritten for the new structure (it monkeypatches `milano_iso.fetch._download` and uses `caplog`).
13. **Regenerated T-1.2 artefact:** `reports/artifacts/T-1.2/summary.json` is rewritten by `dbt_extract` and committed with the new layers (see "What changed"). `schema.md` is unchanged.
14. **Zero-area threshold** is exactly 0 (no slivers are removed) and zero-length is exactly 0; the card gives no tolerance.
15. **Windows line endings:** pipeline steps write text files with CRLF on this machine; I normalised the tracked artefacts I touched to what git stores (LF).

## Open questions and risks
- The drop log is empty on real data. Repair/drop behaviour is covered only by synthetic tests; that is expected for a clean pilot, but the full comune run (Phase 6) will exercise it.
- `make data` takes about 4 to 5 minutes, almost all in the OSM PBF scan (T-1.1 step); well below the 30-minute limit.
- The OSM unassigned counts (many points, `man_made=artwork` areas, `barrier` lines) are listed in `validation.md`; the card says not to invent categories, so they stay unassigned. The orchestrator may decide whether later tasks need more layers (for example trees, `amenity` POIs).
- `validation.md` repeats the sha256 of `pilot.gpkg`; it changes only if the data or the code changes.
