# Decisions (ADR log)

Format: ID, status (Proposed / Accepted / Superseded), context, decision, consequences. The orchestrator confirms or amends every "Proposed" ADR in task T-0.1.

Owner answers to the Phase 0 ASK items were given on 2026-11-15 and are the basis of ADR-0001..0011.

## ADR-0001 - Stack
- **Status:** Accepted (2026-11-15, amended in T-0.1)
- **Decision:** Python pipeline (geopandas, shapely, pyproj, pyogrio, pytest) producing static tiles; web client with Vite, TypeScript and Three.js (vitest, Playwright).
- **Amendment (toolchain pinning):**
  - Python 3.12, managed with `uv`; dependencies locked in `uv.lock` (the system Python on the dev machine is 3.14 and must not be used for the pipeline).
  - Node 24 LTS with `package-lock.json`.
  - GNU make is the task runner (`make data|tiles|test`). On the Windows dev machine it is GNU Make 4.4.1 (winget `ezwinports.make`); on CI it is the runner's native make. Makefile recipes must work in a POSIX shell on both.
- **Consequences:** No backend; hosting is static; the pipeline is reproducible with Make and lockfiles.

## ADR-0002 - True orthographic camera instead of a tilted map
- **Status:** Accepted (2026-11-15)
- **Context:** Mapping libraries with a pitched perspective view do not give a real isometric projection.
- **Decision:** Use Three.js `OrthographicCamera`, with our own tile streaming.
- **Consequences:** More custom code than a map library; exact SimCity-like projection.

## ADR-0003 - Camera angle
- **Status:** Accepted (2026-11-15). The owner confirmed 30 degrees at the Phase 0 checkpoint after seeing the side-by-side render (`reports/artifacts/T-0.2/side-by-side.png`).
- **Context:** Classic SimCity pixel look is a 2:1 dimetric view; "true isometric" is slightly steeper.
- **Decision:** Azimuth 45 degrees, elevation 30 degrees (ground squares appear as 2:1 rhombi). The alternative, 35.264 degrees (true isometric), is rendered side by side in T-0.2 for the owner to compare.
- **Consequences:** Affects shading, texture choices and picking maths. The angle is a single config constant so it can change cheaply until Phase 3.

## ADR-0004 - Coordinates, origin, pilot AOI and tiling
- **Status:** Accepted (2026-11-15)
- **Decision:**
  - Pipeline CRS EPSG:32632. Client coordinates are metres from a fixed origin.
  - **Origin:** the position of the Duomo di Milano taken from a cited source (OSM element and/or Wikidata), transformed to EPSG:32632 and rounded to the nearest whole metre. The value and its citation are recorded in `docs/DATA_SOURCES.md` by T-0.3; no coordinate is typed from memory.
  - **Pilot AOI:** the 1000 m x 1000 m square in EPSG:32632 centred on the origin (origin +/- 500 m on each axis). Final extent: the administrative boundary of the Comune di Milano.
  - **Frozen values (corrected in T-0.3a after G0 blocker B1; verified by the orchestrator with shapely on 2026-11-15):** origin **E 514979, N 5034536** (EPSG:32632). This is the centroid of OSM relation/18017026 "Duomo di Milano" (E 514978.51, N 5034535.58; Overpass base 2026-11-15T19:00:21Z), rounded to whole metres. Pilot AOI bbox **514479, 5034036, 515479, 5035036**. These are constants in `pipeline/milano_iso/config.py` and are never recomputed at build time. The easting is only 0.01 m above a rounding boundary, so a library upgrade must not be allowed to move it. The first recorded value (E 514978, N 5034535) came from a numerically unstable centroid and is void. Wikidata Q18068 P625 lies 83.4 m away, just west of the OSM footprint (the facade side), so it is not used: the footprint centroid matches the landmark-position definition of ADR-0011. Provenance script: `pipeline/scripts/origin_from_sources.py`.
  - Tiles on a 500 m grid aligned to the origin (so the pilot AOI is exactly 2 x 2 tiles), adjustable after measuring size budgets (T-2.1).
- **Consequences:** Avoids floating-point jitter far from the origin; tile boundaries are simple to reason about.

## ADR-0005 - Static delivery on GitHub
- **Status:** Accepted (2026-11-15, amended: owner chose GitHub)
- **Decision:** Source on GitHub; CI on GitHub Actions; site and tiles deployed to GitHub Pages.
- **Risks:** GitHub Pages does not allow custom response headers, so the cache-control and pre-compressed brotli parts of T-6.3 may be impossible there. - **Consequences:** No server costs by default; no runtime dependency on third-party map APIs. CI and deploy need a GitHub repository that the owner creates.

## ADR-0013 - Phase 1 data layout and pipeline step conventions
- **Status:** Accepted (2026-11-15)
- **Decision:**
  - `data/raw/<source>/` holds downloaded files, unchanged. `data/interim/` holds per-source extracts in the source CRS. `data/processed/` holds normalised layers in EPSG:32632. All three are gitignored. Every path derives from `config.DATA_DIR`, which the env var `MILANO_ISO_DATA` can override (so parallel worktrees share one download cache). Manifests and the `pipeline/manifests/` folder always stay in the repo.
  - Every downloaded file has a committed manifest `pipeline/manifests/<source>.json` with url, retrieval date (UTC), byte size and sha256. Fetch steps are idempotent: they skip the download when the file exists and its sha256 matches the manifest, and fail loudly on a mismatch.
  - Each pipeline step is a module run as `uv run python -m milano_iso.<step>`. Each step's Make targets live in their own fragment `pipeline/mk/<step>.mk`, which appends to `DATA_STEPS`. This lets parallel tasks avoid editing a shared Makefile.
  - **Processing extent:** a feature is kept when it intersects the extent, and is kept whole (no cutting at the extent edge). Phase 1 uses the pilot AOI (ADR-0004); Phase 6 uses the comune boundary.
  - Landmarks are located by Wikidata QID, which is then resolved to the OSM element tagged with it. Their positions follow ADR-0011.
- **Consequences:** Reruns are cheap and deterministic. A changed upstream file is detected rather than silently used.

## ADR-0014 - Building geometry: DBT volumes first, OSM for attributes and gaps
- **Status:** Accepted (2026-11-15)
- **Context:** T-1.2 showed that the DBT 2020 of the Comune di Milano (CC BY 4.0, scale 1:1,000) splits every building into volume units (`UN_VOL`), each with its own height. In the pilot there are 4,657 volumes for 170 `EDIFC` buildings. `UN_VOL_AV` is the height of a flat-topped volume up to the eaves (spec pp.129-133). OSM has 706 building areas in the pilot, with names and types but sparse heights.
- **Decision:**
  - Rendered building massing comes from DBT volumes wherever DBT covers a building: each volume is extruded from its base to its top, with `height_source = dbt`.
  - OSM supplies attributes (name, `building` type, OSM id for the info card), joined spatially to the DBT buildings.
  - OSM buildings with no DBT counterpart (for example, built after the 2020 survey) are rendered from their OSM footprint. They use the height fallback chain steps 2-5 of `DATA_SOURCES.md`.
  - Both the Comune di Milano (CC BY 4.0) and OSM (ODbL) are credited in the UI.
- **Consequences:**
  - The geometry is far more accurate (roof steps, courtyards, towers on podiums), and the landmarks gain real massing.
  - Conflating DBT and OSM needs explicit, tested matching rules (T-1.4).
  - Completeness (VERIFICATION section 3) is measured per source: processed DBT volumes >= 99% of the source volumes in the extent, and processed OSM buildings >= 99% of the OSM building areas.

## ADR-0015 - Height rules for v1
- **Status:** Accepted (2026-11-15)
- **DBT volumes:**
  - Each volume spans from `bottom = UN_VOL_QE - UN_VOL_AV` to `top = UN_VOL_QE`, measured relative to the building's ground level.
  - **Ground level** is the minimum base Z of the building's ground-based volumes (`POR` 01). A building with no `POR` 01 volume uses the minimum base Z of all its volumes and is flagged.
  - Basis: the spec, pp.129-133 (flat-topped volume to eave level, portico intrados). The pilot data agree: for `POR` 01 and 04, `QE - AV` equals the base Z within 0.001 m; for `POR` 03 (porticoes) the volume starts 3.5 m above its base, so the open space under the portico stays empty.
  - No roof shapes are added: the model is flat-topped at eave level.
- **Overture (step 4 of the fallback chain) is skipped in v1.** T-0.3 found that Overture building heights come mainly from OSM, so the step adds little; and Overture was not fetched. Revisit in Phase 6 if many buildings fall through to the default.
- **Default height (step 5)** *(superseded by ADR-0016)* is derived from data, never typed: the median building height of DBT buildings matched to OSM buildings with the same `building` value in the processed extent, when there are at least 5 of them. Otherwise it is the median over all matched DBT buildings. The values are written to a committed artifact by the pipeline, and every such building has `height_source = default`.
- **OSM levels:** `building:levels x 3.0 m` with no roof allowance, as in `DATA_SOURCES.md`.

## ADR-0016 - Default height and non-solid OSM buildings (amends ADR-0015)
- **Status:** Accepted (2026-11-15)
- **Context:** In T-1.4, 18 of the 22 OSM buildings with no DBT counterpart got the default height. Under ADR-0015 that is the median of DBT buildings of the same `building` type, about 28-34 m. That median comes from large `EDIFC` buildings and is biased. The DBT 2020 is a 1:1,000 survey, so a structure that OSM has but the DBT does not is much more likely to be minor or not a solid building. Examples in the pilot are a medieval crypt (San Giovanni in Conca), an underground shop entrance, roofs without walls (the Galleria's glass roof), and construction sites. A 30 m block at those places would be a visible error.
- **Decision:**
  1. The default height (step 5) is the median height of the DBT `EDI_MIN` (minor building) buildings in the processed extent: 3.2 m (n = 47) in the pilot, as measured by the orchestrator. The pipeline computes and records this value; it is not typed.
  2. OSM buildings with `building=roof` or `building=construction` that have no DBT match are kept in `buildings` but **not rendered**: `rendered = false` and `render_reason` set. Landmark roofs (the Galleria) are modelled in Phase 4.
  3. Every unmatched building stays listed in `unmatched_osm.csv` for review. A tall building built after 2020 without OSM height tags would show up too low; that is an accepted, visible gap.

## ADR-0017 - Checking positions when rendered buildings come from the DBT
- **Status:** Accepted (2026-11-15)
- **Context:** T-1.6 check 7b compared each landmark's reference position (the centroid of its OSM footprint, ADR-0011) with the centroid of the rendered DBT building(s). It failed for Palazzo Reale (18.5 m) and Torre Velasca (5.2 m). The OSM and DBT data draw a building's extent differently: a DBT building unit can include wings or a podium that OSM maps as separate buildings, so their centroids differ even when both are correctly placed. It failed for Palazzo delle Assicurazioni Generali because no rendered building got its `landmark_id`: the attribute transfer works from the DBT building outwards, and the overlapping DBT building took another OSM id.
  - **Orchestrator measurement:** I took the 41 OSM/DBT building pairs with IoU >= 0.8 in the pilot and compared their centroids. The mean offset is (dE +0.21 m, dN -0.08 m), the median distance 0.34 m and the p95 3.5 m. There is no systematic misregistration between the two sources.
- **Decision:**
  1. `landmark_id` is assigned landmark-first. The rendered building with the largest overlap with the landmark's OSM footprint is the primary building. Any other rendered building with more than 50% of its area inside that footprint also gets the id.
  2. **Rendered landmark check:** the reference position must lie inside the primary rendered building's footprint, or within `tolerance_m` (5 m) of it. The IoU between the OSM landmark footprint and the rendered footprints that carry the id is reported, not asserted.
  3. **Registration check:** over OSM/DBT pairs with IoU >= 0.8 (at least 20 pairs), the magnitude of the mean centroid offset vector must be <= 1.0 m. The baseline is 0.22 m; this check catches a CRS or datum shift.
  4. The pipeline-integrity check (7a, OSM footprint centroid within 5 m of the reference) is unchanged.

## ADR-0018 - Courtyards and deferred landmarks in the rendered landmark check (amends ADR-0017 point 2)
- **Status:** Accepted (2026-11-15)
- **Context:**
  - **Palazzo Reale:** after T-1.6a its reference position (the OSM footprint centroid) lies in the DBT courtyard of the palazzo, 22.3 m from the primary rendered building and 10.4 m from the nearest building carrying its id. The centroid of a building wrapped around a courtyard often falls inside the courtyard, so the point check was testing the shape, not the placement.
  - **Galleria:** landmark-first assignment gave its id to an unrelated building (IoU 0.006), even though its own OSM roof is not rendered (ADR-0016).
- **Decision:**
  1. The rendered landmark check measures the distance from the reference position to the union of all rendered buildings carrying the landmark id; the union is formed first and its interior rings (courtyards) are then filled. A courtyard enclosed by several buildings (Palazzo Reale) therefore counts. The tolerance stays 5 m.
     - The orchestrator measured this on 2026-11-15: all 6 rendered in-pilot landmarks are at 0.00 m, against 22.26 m for Palazzo Reale and 2.39 m for Generali under the old primary-only rule.
     - The registration check (ADR-0017 point 3) still guards against any systematic shift.
  2. A landmark whose own OSM element is not rendered (`rendered = false`) gets no `landmark_id` assignment at all and is reported as `deferred_phase4`.
- **Owner note:** this changes how the check measures, not the 5 m threshold. It is flagged to the owner at the G1 report.
- **Superseded in part:** point 1 is replaced by ADR-0020 (owner decision, 2026-11-15). Point 2 stays.

## ADR-0019 - Threshold for the share of explicit heights
- **Status:** Accepted (2026-11-15)
- **Context:** VERIFICATION section 3 says the baseline share of explicit (non-default) heights is measured at G1, after which an ADR fixes the threshold. G1 measured it on the pilot: 92.5% of buildings by count and 99.1% by footprint area.
- **Decision:** On the pilot, `make validate` asserts an explicit share of at least **90% by count** and at least **98% by footprint area**. These are about 2.5 and 1 percentage points below the baseline, to absorb small upstream data changes. For the whole city (Phase 6) the baseline is measured again and the threshold re-set by a new ADR before G6.

## ADR-0020 - Best-fit offset check for landmark placement (replaces ADR-0018 point 1)
- **Status:** Accepted (2026-11-15; owner approved at G1)
- **Context:** At G1 the reviewer shifted the Duomo's rendered building 40 m in a scratch copy, and the ADR-0018 check still passed (the reference point stayed inside the filled footprint). A check that cannot fail is not a check.
- **Decision:**
  - For each in-extent landmark with a rendered building, take its OSM footprint F and R, the union of the rendered footprints that **carry that landmark's id** (interior rings filled). *Amended 2026-11-16 (T-1.7 finding):* the original R, every rendered footprint within 60 m, let F slide to a better-covered spot in the dense centre. Palazzo Marino moved 70.2 m and Torre Velasca 50.7 m on correct data. The search window stays +/-50 m so that large shifts are still detected.
  - Find the translation t, within +/-50 m, that maximises area((F + t) intersected with R). Search on a 2 m grid, then refine on a 0.25 m grid around the best cell. If several t come within 0.5% of the maximum overlap, take the one with the smallest |t|.
  - **The landmark passes when |t| <= `tolerance_m` (5 m).** The best overlap ratio and the width of the plateau of near-maximal overlaps are reported.
  - The registration check (ADR-0017 point 3) and the pipeline-integrity check 7a stay as they are.
- **Known limitation:** when F lies well inside a much larger DBT block (Generali), the overlap plateau is wide, so the check is weak for that landmark. The plateau width is reported so the weakness is visible.

## ADR-0021 - Tile scheme and format (task T-2.1)
- **Status:** Accepted (2026-11-15)
- **Grid:** square 500 m tiles in EPSG:32632, aligned to the origin of ADR-0004.
  - Tile (i, j) covers E0 + 500*i <= E < E0 + 500*(i+1), and the same for N with j.
  - The pilot AOI is exactly tiles i, j in {-1, 0}: 4 tiles.
- **Client coordinates:** metres relative to the origin, Y up: x = E - E0, y = height, z = -(N - N0). float32 is enough: at 15 km from the origin its precision is about 1 mm.
- **Assignment:**
  - **Buildings** go whole to the single tile that contains the representative point of their `buildings` footprint. All their render volumes follow them. They are not split.
  - **Lines and areas** (roads, rail, water, green, road_areas, landuse) are clipped at tile edges, which VERIFICATION section 3 allows as "explicitly split".
  - Rows with `rendered = false` are excluded.
- **Format:** one binary glTF 2.0 file (`.glb`) per tile, written by our own deterministic writer (numpy + struct) so the output is byte-identical.
  - One mesh per layer, using float32 positions and normals and uint32 indices.
  - A per-vertex `_FEATURE_ID` (uint32) points into a sidecar `<tile>.json` feature table holding key, name, type, `height_m`, `height_source` and `landmark_id`, used for picking in Phase 5.
  - No textures. Colour and material are decided in the client (Phase 3).
- **Geometry:**
  - **Building footprints** are simplified with `simplify(0.2, preserve_topology=True)`. The Hausdorff distance to the original must be <= 0.5 m (VERIFICATION section 3), checked per feature.
  - **Buildings** are extruded from `bottom_m` to `top_m`: walls plus a flat top, and a bottom face only when `bottom_m > 0`.
  - **Flat layers** are triangulated at small fixed heights (style constants) to avoid z-fighting.
- **Road ribbon widths:**
  - An OSM `width` tag is used where it parses.
  - Otherwise the width comes from a per-class **style table** in the pipeline config. These widths are stylisation, labelled as such, and are not presented as measured data.
- **Manifest:** `tiles.json` with the format version, CRS, origin and tile size, and per tile: id, bbox (both local and EPSG:32632), counts per layer, byte size, gzip size and sha256. Validated against a committed JSON Schema (T-2.3).
- **Budget:** 250 KB gzip per tile (VERIFICATION section 5). Measured in T-2.2; if exceeded, the tile size or the format is revisited by ADR.

## ADR-0022 - Compact tile encoding (amends ADR-0021 format); all intersecting buildings exported
- **Status:** Accepted (2026-11-16)
- **Context:** T-2.2 measured all 4 pilot tiles above the 250 KB gzip budget: 379-662 KB, with 13.7 MB of raw glb in total. Buildings dominate (tile 0_0: 128,763 vertices for 42,921 triangles). The export is effectively non-indexed: three vertices per triangle, with float32 normals and float32 positions.
- **Decision:**
  1. **No `NORMAL` attribute.** The client uses flat shading, with normals derived in the shader from screen-space derivatives (three.js `flatShading: true`). Vertices are then shared through indices: each ring vertex is stored once at the bottom and once at the top of its volume.
  2. *(Amended 2026-11-16, see point 2a.)* **Quantised positions (`KHR_mesh_quantization`, required extension).** `POSITION` is int16 (normalized=false). The values are centimetre offsets from the tile's south-west corner at y = 0, with the node's translation set to that corner in client metres and its scale to 0.01.
     - Range: +/-327.67 m per axis. That covers a 500 m tile only if the offset starts at the tile centre, so the offset is taken **from the tile centre** instead.
     - Heights up to 327 m fit (the pilot maximum is 100.2 m). A feature exceeding the range makes the export fail loudly.
     - Rounding to 1 cm is far below the 0.5 m simplification tolerance.
  2a. **Amendment (T-2.2a finding).** Buildings are kept whole, so they overhang their tile. The worst case is dbt:EDIFC_5112, 358.9 m from its tile centre. Seven buildings, the Duomo among them, exceed +/-327.67 m.
     - **The quantisation unit becomes 2 cm:** node scale 0.02, centred on the tile centre, which gives a range of +/-655.34 m.
     - The maximum rounding error is 1 cm, far below the 0.5 m simplification tolerance.
     - Out-of-range coordinates still fail loudly. Phase 6 must re-check the worst overhang for the whole city.
  3. **Smallest index and id types.** `uint16` indices for meshes with fewer than 65,536 vertices (otherwise the mesh is split into chunks named `<layer>#<n>`). `_FEATURE_ID` is `uint16` when the tile has fewer than 65,536 features, else `uint32`.
  4. If the tiles are still over budget after 1-3, the next step is a smaller tile size (250 m), decided by ADR with measurements. Mesh compression (meshopt or Draco) is not adopted: it adds a dependency and a decoder.
  5. **All intersecting buildings are exported.** A rendered building whose representative point falls in a tile outside the 2 x 2 pilot block still gets exported, in that tile. Every feature then appears in exactly one tile, and edge tiles may hold only those buildings.
  6. **Underground roads and rail** (`underground = true`) are not exported in v1. Confirmed from T-2.2's assumption.

## ADR-0023 - Tile size 250 m (amends ADR-0021)
- **Status:** Accepted (2026-11-16)
- **Context:** After the compact encoding (ADR-0022), tile 0_0 is still 289,508 bytes gzip-9 against the 256,000 budget. The other 500 m tiles are 7.9-237 KB. ADR-0022 point 4 names a 250 m tile size as the next step, to be taken with measurements.
- **Measurement:** the orchestrator ran the T-2.2a exporter with the tile size patched to 250 m in a scratch copy on 2026-11-16. It produced 30 tiles; all 233 rendered buildings appear exactly once; the four largest tiles are 66.9, 81.6, 86.7 and 92.0 KB gzip-9.
- **Decision:**
  - Tiles are **250 m** squares aligned to the origin. Tile (i, j) covers E0 + 250*i <= E < E0 + 250*(i+1), and likewise for N with j. The pilot AOI is tiles i, j in {-2..1}: 16 tiles.
  - The tile size becomes a single constant `TILE_SIZE_M` in `pipeline/milano_iso/config.py`, recorded in `tiles.json`.
  - The quantisation (ADR-0022 point 2a: 2 cm from the tile centre, +/-655 m) still fits, since whole buildings overhang by at most a few hundred metres. The export keeps failing loudly if a building exceeds the range.
- **Consequences:** about 4 times more requests per area, still far within the draw-call budget (16 tiles x about 6 meshes for the pilot). The budget headroom (largest tile about 36% of 256 KB) leaves room for denser districts in Phase 6, where it is measured again.

## ADR-0015 amendment - Ground level of raised-only DBT buildings (T-1.7)
- **Status:** Accepted (2026-11-16)
- **Decision:** A DBT building with no `POR` 01 volume takes as its `ground_z` the median `base_z_min_m` of the `POR` 01 volumes of other buildings within 50 m of its footprint. It needs at least 5 such volumes; with fewer it widens to 100 m, and with still fewer it fails. It is flagged `ground_flag = neighbour_median` with the count in `ground_neighbours`. This replaces "the minimum base Z of all its volumes".
- **Evidence:** EDIFC_2671, an underpass ceiling (`POR` 04): with 83 neighbours it now spans 3.44-19.34 m, where before it was 0-15.9 m and filled the passage.

## ADR-0024 - CI toolchain pinning
- **Status:** Accepted (2026-11-17)

## ADR-0026 - Per-tile building materials (amends T-3.3 spec)
- **Status:** Accepted (2026-11-17)
- **Context:** Building colour comes from a per-tile lookup texture indexed by `_feature_id`. three.js does not re-upload a shared material's uniforms between draws of different meshes, so one shared building material cannot switch the lookup per tile.
- **Decision:**
  - Building meshes use one material instance per (tile, mesh). All of these share a single compiled shader program through `customProgramCacheKey`, so the draw-call count is unchanged (measured: 111 draw calls at the default real view with shadows).
  - Flat layers keep one shared material each.
  - Colours, sun direction and shadow settings are style constants in `web/src/style/` and are not data.

## ADR-0027 - No MSAA in e2e runs
- **Status:** Accepted (2026-11-17)
- **Context:** With continuous rendering (T-3.4 benchmark), headless Chromium on SwiftShader logs `GL_INVALID_OPERATION: glBlitFramebuffer: Blit feedback loop` at random moments. Our code has no render targets and never reads the canvas. The experiment by the executor: about 3 occurrences in 24 runs with `antialias: true`, 0 in 48 runs with `antialias: false`. The orchestrator confirmed after the fix: 40/40 runs of `debug.spec.ts` passed. The most likely source is the browser's own resolve of the multisampled default framebuffer.
- **Decision:**
  - The renderer is created with `antialias: !e2eEnabled()`. Production and `?debug` keep antialiasing; only `?e2e=1` runs drop it.
  - The console filter (ADR-0012) is not widened.
  - Visual-regression baselines (G3 and later) are captured under `?e2e=1`, so baselines and test runs stay consistent.
- **Consequence:** e2e screenshots are not antialiased. Antialiasing is checked on real devices at the checkpoints.

## ADR-0032 - UI language runtime, shared UI colours, focus indicator and contrast criterion (T-5.4)
- **Status:** Accepted (2026-11-17), pending the G5 review
- **Decision:**
  - **Language (ADR-0006):** `i18n.ts` holds the language in use. The initial language is `?lang=it|en`, then the choice remembered in `localStorage` (`milano-iso.lang`, written only by a click on the IT/EN button), then Italian. `t(key)` reads the language in use; every module re-labels itself through `onLangChange`, so the switch is live (including `<html lang>`, aria-labels, the tiles notice and the info card). Feature names and the attribution entries are data and are never translated. A grep-based unit test (`i18n.test.ts`) fails on any literal user-facing string in the DOM code of `web/src`; its allow-list is in the test, each entry with its reason.
  - **One UI stylesheet:** the buttons, search box, list rows, notice, card and attribution use the same CSS variables (`--tb-*`, day and night, in `index.html`). The rotation buttons and the day/night toggle are no longer styled inline. This is UI style only; the map palette (ADR-0030) is unchanged.
  - **Targets:** every control is at least 44x44 CSS px. The check boxes of the layers panel are the whole 44 px row (the native input covers it). The attribution links and the card's OSM link are 44 px tall.
  - **Focus indicator:** a 3 px ring with a 2 px halo on each side (day: dark blue `#08306b` between white bands; night: amber `#ffd54f` between `#263238` bands). The map container draws the same on a pseudo-element over the canvas.
  - **Contrast criterion over a map that is light, mid and dark:** a single border or ring colour cannot reach 3:1 against every map colour (measured: a dark-grey border reached 1.57:1 on a tan roof). WCAG 1.4.11 asks for 3:1 for whichever part identifies the component, so a boundary counts when its border OR its own fill reaches 3:1, and a focus indicator when its ring OR its halo does. Border colours are therefore extreme (day `#1c262b`, night `#ffffff`), so the border and the fill cover complementary lightness ranges. Text is measured as the text colour against the control fill composited over the real map pixels (>= 4.5:1). `web/scripts/measure-contrast.mjs` does this on the real tiles.
  - **Tab order:** toolbar, map, the controls at the right (day/night, rotation), the info card, the attribution (the right-hand controls and the card are inserted before the attribution in the DOM).
  - **Tile retry:** a tile waiting for its retry counts as loading but holds no loader slot, and is retried only if still wanted.
- **Consequences:**
  - The win32 visual baselines that show the day/night toggle or the attribution were regenerated (the map pixels are unchanged, checked outside the UI boxes). The `*-linux.png` files are stale until the `visual-baselines` workflow is rerun.
  - The `?debug` overlay moves to the bottom on screens 600 px wide or less, so it does not cover the tiles notice.
  - Any new colour in the UI must be added to the measurement (`measure-contrast.mjs`) and keep the same ratios.

## ADR-0033 - Index kind `stop`: platforms are not streets (T-5.6, amends ADR-0031)
- **Status:** Accepted (2026-11-18), pending the review
- **Decision:**
  - **Rule (tags only, never names):** an OSM way with `public_transport=platform`, `highway=platform` or `railway=platform` is a platform. A platform is never part of a `street` entry. Platforms with a name form a new index kind `stop` (IT "Fermata", EN "Stop"), grouped by exact name like streets, ref `{"osm_ids": {"w": [...]}}`. Its bbox and centre come from its own ways.
  - **Streets keep only their own ways.** A street that shares a name with a platform (Largo Augusto, Piazza Fontana, Via Larga) is built from its street ways only, so its bbox and centre no longer include the platform.
  - **Not moved:** footways, steps and `footway=sidewalk` ways that are not platforms stay streets. In the pilot they are real named passages and galleries (Galleria Pattari, Galleria Unione, Passaggio Duomo, Via Speronari, Via Brolo); a rule that dropped them would remove real streets from search. "Nuovo accesso M3" (footway + steps, no platform tag) therefore stays a street: no tag says it is a stop, and the pipeline does not use name patterns.
  - **Tag carried through the pipeline:** `normalise.py` adds a boolean column `is_platform` to the `roads` layer (`classify.is_platform(tags)`). The processed layer had no platform information (class `footway` for most), and the tags exist only in `interim/osm_pilot.gpkg`; the OSM extract step is unchanged. `tiles/export.py` reads the column, never writes it to the tile tables, and passes `platform` on the street records to `tiles/index.py`. A processed layer without the column (the e2e fixture) means no platforms.
  - **Format:** `KIND_ORDER` gets `stop` appended (append-only). `INDEX_FORMAT_VERSION` stays 1: a client that does not know `stop` drops those entries (`parseIndex`), and the new client reads old indexes unchanged.
  - **Client:** `stop` maps to the same `FeatureRef` as a street (`layer: roads`), so the card shows the real road class. Ranking: an exact folded-name match first, then landmarks before other kinds among prefix matches, then the previous order (folded name, kind, name). The search label of a landmark is now "Punto di riferimento" (IT), the card's term; EN stays "Landmark".
- **Consequences:** real pilot data: 184 street entries become 176 and 11 `stop` entries appear (`reports/artifacts/T-5.6/index_before_after.txt`). The 8 street entries that disappeared consisted only of platform ways. `processed/pilot.gpkg` `roads` has one more column.

## ADR-0035 - Processing extent parameter and no partitioning (T-6.1)
- **Status:** Accepted (2026-11-19)
- **Context:** Phase 6 runs the pipeline on the whole comune (ADR-0013). Every step was written for the pilot box.
- **Decision:**
  - **One parameter.** Every step takes `--extent pilot|city`; the Make fragments take it from `EXTENT ?= pilot`. `make data tiles validate` with no variable builds the pilot exactly as before (tiles byte-identical to the reference, committed pilot artefacts unchanged). `milano_iso/extent.py` is the only place that knows the extents and derives the paths.
  - **Extents.** `pilot` is `box(PILOT_AOI_BBOX)`. `city` is the comune boundary in `raw/comune_boundary`, reprojected to EPSG:32632 (one geometry). Features that intersect the extent are kept whole (ADR-0013); the tile grid (250 m, origin of ADR-0004) is the same for both. The tiles of an extent are the grid tiles that intersect it, plus the tiles of the rendered buildings and landmark details (ADR-0022 point 5). Flat layers are clipped to the bounding box of the extent (for the pilot, the AOI box, as before).
  - **Paths.** The pilot paths are unchanged (`interim/osm_pilot.gpkg`, `interim/dbt_pilot.gpkg`, `processed/pilot.gpkg`, `processed/drop_log.csv`, `tiles/pilot/`, `reports/artifacts/T-1.*`..`T-4.*`). Another extent gets `interim/osm_<extent>.gpkg`, `interim/dbt_<extent>.gpkg`, `processed/<extent>.gpkg`, `processed/drop_log_<extent>.csv`, `tiles/<extent>/` and `reports/artifacts/T-6.1/<extent>/<original artefact dir>/`. The JSON key that holds the canonical sha of a GeoPackage is `canonical_dump_sha256_<extent>_gpkg` (for the pilot this is the old `..._pilot_gpkg`).
  - **Measuring.** `milano_iso/measure.py` (standard library only) runs one step as a child process and records wall seconds, peak working set (the largest single process of the tree: a venv `python.exe` is a launcher that starts the real interpreter) and the row counts the step reports, into `reports/artifacts/T-6.1/measurements.json`. Make uses it by default for every extent except the pilot (`MEASURE=1` forces it).
  - **Tile export without a per-tile scan.** The export looked at every building and every flat polygon for every tile; with the city that is quadratic. Buildings are grouped by tile once and each flat layer has an STRtree (`_FlatIndex`) that returns, per tile, the same polygons in the same order as the scan did. The pilot output is byte-identical.
  - **Boundary tolerance.** The check "every feature intersects the extent" accepts a miss of up to 1e-6 m. A named line clipped to the comune polygon is reduced to a point on its surface that can land on the boundary; 38 of 68426 named features missed `intersects` by about 1e-10 m.
  - **No partitioning.** The measured steps stay far below the limits of the card (24 GB peak, 2 h): see the table in `reports/R-6.1.md`. Partitioning would risk the byte identity and is not introduced. Revisit if a later step exceeds the limits.

## ADR-0036 - Whole-city heights and style gaps: own-base ground, zero heights, road widths (T-6.1, owner decisions of 2026-11-19; amends ADR-0016)
- **Status:** Accepted (owner decision 2026-11-19); extensions B and D confirmed 2026-11-19
- **Context:** the first full-city run stopped on three things the pilot never met (`reports/R-6.1.md`, BLOCKED report of 902cc34).
- **Decision:**
  - **A. Ground of a building with no ground-level volume and fewer than 5 neighbours.** The rule of ADR-0016 is unchanged (median `base_z_min_m` of the POR 01 volumes of other buildings within 50 m, then 100 m, at least 5). When it still finds fewer than 5, the building takes its own lowest `base_z_min_m` over all its volumes as ground. The volumes get `ground_flag = own_base` (new value next to `neighbour_median`; `ground_neighbours` stays empty) and the building is listed in `ground_own_base_log.csv`. It applies to any such building. The city has one: `EDIFC_2797`.
  - **B. Volumes with no height.** A DBT volume with `UN_VOL_AV` of zero or less gets `height_m` = the default height of ADR-0016, `height_source = default`, `top_m = bottom_m + default`, one row in `height_default_log.csv`. Such volumes do not take part in deriving the default (the building heights used for the median come from the other volumes; a building with only zero-height volumes is left out). A building whose tallest volume is a defaulted one has `height_source = default`. The same rule is applied to an OSM prism whose top is not above its bottom (`kind osm_prism` in the log). Without it the check `height_m > 0` fails on one OSM bridge (levels 1, min_level 1). The extension to the 2 volumes of -0.001 and the OSM prism was confirmed by the owner on 2026-11-19. The city has 284 DBT volumes with `UN_VOL_AV` = 0, 2 with -0.001 (same defect, treated the same) and 1 such OSM prism: the 287 rows of the first report are 284 + 2 + 1.
  - **C. Style widths** (style, not data; an OSM `width` tag still wins): roads `motorway` 12, `trunk` 10, `primary` 9, `secondary` 8, `living_street` 5, `track` 3, `other` 4; rail `rail` 3 metres. A class still missing is an error.
  - **D. Buildings entirely below ground (found by the full run; rule confirmed by the owner on 2026-11-19).** Six DBT buildings consist only of POR 08 volumes that lie below ground level (every top is at most 0; `max top` -0.025 to -1.091 m), so the building `height_m` (the largest top) was negative and the check `height_m > 0` failed on the `buildings` layer. Their `height_m` is now the thickness of their thickest volume (2.748 to 4.099 m, source stays `dbt`; listed in `building_below_ground_log.csv`). The volumes, their rendering and the default height (derived before this step) are unchanged.
- **Consequences:** the pilot has no such case, so its outputs are byte-identical (no new log files, no new report keys appear for it). The new log files are written only when non-empty.

## ADR-0037 - Levels of detail: coarse blocks, an error bound in pixels, a quantisation unit per level (T-6.2)
- **Status:** Accepted (owner decisions of 2026-11-20: points 5 and 6 accepted, the quadtree split of point 7 decided; proposed by the executor of T-6.2).
- **Context:** the whole comune is 3,139 base tiles of 250 m. At 1200 m visible width on 1280x720 the base level already needs 448 draw calls at the origin (measured), against the budget of 300, and at 4000 m on a phone far more. The client must show coarse tiles when zoomed out and the 250 m tiles when zoomed in.
- **Decision:**
  1. **Error bound, not taste.** `tiles.json` has a `levels` array (schema updated). Level 0 is the base tiles (`tiles`, tolerance 0.2 m, the footprint simplification of ADR-0021). Every other level records `tolerance_m`, `block_m`, `unit_m`, what it keeps, its `tiles` (ids `L<n>_<i>_<j>`, files `L<n>_<i>_<j>.glb` and `.json` next to the base tiles) and its totals. The client uses the coarsest level whose `tolerance_m` is at most the current metres per pixel (visible width divided by the viewport width in CSS pixels); level 0 is always allowed. Going to a finer level waits until the metres per pixel are below 0.85 times the current level's tolerance (hysteresis, a UX constant).
  2. **The levels** (`pipeline/milano_iso/tiles/lod.py`, one table):

     | level | block | tolerance | unit | buildings kept | other layers |
     |---|---:|---:|---:|---|---|
     | 1 | 500 m | 0.5 m | 0.02 m | footprint 20 m2 or more, or named, landmark, or 40 m tall or more | landuse, green, water, road areas, rail, roads of the classes motorway to tertiary, residential, unclassified, living_street, pedestrian |
     | 2 | 1,000 m | 1.5 m | 0.04 m | footprint 40 m2 or more (same exceptions) | the same |
     | 3 | 2,000 m | 3 m | 0.04 m | footprint 300 m2 or more (same exceptions) | landuse, green, water, roads motorway to tertiary |

     All levels drop road markings, trees and landmark details (smaller than a pixel at these scales), and the road classes footway, cycleway, steps, path, service, track, platform and `other`. Blocks are whole multiples of the 250 m grid and nest. The numbers come from measurements (`reports/artifacts/T-6.2/`): with these three levels and the split of point 7 every measured view is within 300 draw calls (largest 293) and no tile is over 250 KB gzip. Level 3 starts at 3 m per pixel because with 5 m the widest desktop view (1280x720, 4000 m = 3.1 m per pixel) used level 2 and needed 396 calls after the split.
  3. **What a level may do to the data, and only this:** simplify polygon outlines (Douglas-Peucker, topology kept) within the level tolerance, measured per piece and checked at build time (the build fails above the tolerance); merge the volumes of one building whose bottom and top fall in the same vertical step (step = 2 x tolerance, so the height error is at most the tolerance, **accepted by the owner on 2026-11-20 as the meaning of "heights stay real" for coarse levels**; a volume that would round to nothing gets half a step, so a low annex keeps its footprint; a union removes only joins between equal heights; a volume wholly below ground is not drawn); drop a piece whose bounding box is not larger than the tolerance; drop a building below the area limit unless it is named, a landmark or tall (**every dropped key is written to `lod_dropped_buildings.csv` with its reason**; the pilot's file is committed); drop whole layers and road classes as in the table. Positions never move by more than the tolerance and nothing is added. Buildings keep their key and every field of their base feature-table row (tested equal), so the card shows the same data at any zoom.
  4. **Determinism (CLAUDE.md lesson).** Coarse polygons are snapped to the level's grid (`shapely.set_precision`) and rebuilt from integer steps with a fixed ring orientation and start vertex; pieces are sorted. The base tiles, `index.json` and the pilot minimap are untouched (the pilot's base .glb and feature .json files are byte-identical to the reference; only `tiles.json` gains `levels`).
  5. **Quantisation unit per level (amends ADR-0022 2a for the coarse levels; accepted by the owner on 2026-11-20).** The 2 cm unit (+/-655 m from the tile centre) fits 500 m blocks (worst offset 507 m) but not 1 km blocks (worst 757 m; the first city run failed on a 690 m offset) nor 2 km blocks. Levels 2 and 3 use a 4 cm unit (+/-1,310 m); the unit is in the node scale of each glb and in `levels[].unit_m`, so the client needs no change. The top-level `quantization.unit_m` and level 0 stay 0.02. **Measured worst offsets from a tile centre in the final city build, after the split of point 7: level 1 507.26 m (range 655.34), level 2 757.28 m (range 1,310.68), level 3 1,218.04 m (range 1,310.68; 92 m of headroom).** Out-of-range coordinates still fail the export loudly.
  6. **No hole, no double drawing.** The streamer loads tiles of every level; the client draws exactly one level per piece of ground. A coarser tile that is loaded stays while any visible tile of the chosen level inside it is still missing (and the chosen tiles inside it are hidden); a loaded chosen tile is drawn unless such a tile covers it; a missing chosen tile is covered by the loaded tiles of the nearest finer level. This is a pure function (`web/src/tiles/levels.ts`, `planDraw`), tested over every combination of loaded tiles, and e2e on the fixture with levels. A hidden tile is not pickable.
  7. **Tiles over 250 KB gzip are split in four (quadtree; owner decision of 2026-11-20).** A coarse tile whose .glb is over `max_tile_gzip_bytes` (250,000, recorded per level in `tiles.json`) is deleted and rebuilt as its four quarters (cell size halved, buildings assigned to the quarter by their representative point, flat layers clipped to it, quantisation centred on the quarter), and so on until every tile fits (the build fails after 4 splits). Quarter ids are `L<n>_<i>_<j>q<digits>` (one digit 0..3 per split), each with its own `bbox_local`; an empty quarter is not written. The cells of one level never overlap. Because the client works with cells (`bbox_local`), the rule of point 6 needs no change: a quarter is drawn when loaded, a coarser stale tile stays while any visible quarter under it is missing, and a missing quarter is covered by the finer level under it (vitest over every combination of loaded tiles). Result in the city: level 1 none split (836 tiles); level 2 13 parents split into 52 quarters (267 tiles); level 3 13 split into 52 (107 tiles); largest tile 200,465 / 245,977 / 246,979 B. The gzip figure is the pipeline's (Python zlib); another zlib could decide a split differently near the limit, so the check of Linux byte identity is the one in CI.
  8. **City minimap.** For any extent other than the pilot the minimap is drawn from water, green and the major road classes only (no buildings, no minor roads), simplified at 12 m, with green and water pieces under 20,000 m2 dropped: 390,352 bytes raw, 149,048 gzip (from 7.3 MB and 2.6 MB), real geometry from the same layers. The pilot minimap is not changed (the rule is not applied to it).
- **Consequences:** the city has 836, 267 and 107 coarse tiles (26.7, 18.4 and 10.0 MB gzip, against 64.5 MB for the base tiles); every tile is at most 250,000 B gzip (largest 246,979 B); every measured view fits in 293 draw calls. The split costs draw calls (more, smaller tiles) and bytes (10.0 MB at level 3 against 6.6 MB unsplit with a 5 m tolerance; the tolerance there is now 3 m). `tiles.json` grows to 2.36 MB raw and 675 KB gzip (from 1.7 MB and 468 KB): T-6.3. The visual-regression fixture has no levels, so no baseline meets a coarse level; the e2e of level switching uses a second fixture (`fixtures/tiles-lod`).

## ADR-0038 - Sharded manifest, content-hash URLs, precompressed assets and cancelled requests (T-6.3)
- **Status:** Accepted (owner decisions of 2026-11-20). **Budget reading (owner):** the initial payload is the bytes on the wire until the default view is completely drawn, as served with brotli; the prefetch ring loads after it and is not counted; 3 MB means 3,000,000 bytes. The host chosen in Phase 7 (T-7.3) must serve the precompressed `.br` files with `Content-Encoding: br`: with gzip only, the phone default view is 4.44-4.63 MB (over budget).
- **Context:** after T-6.2 `tiles.json` of the city was 2.36 MB raw / 675 KB gzip and had to be fetched and parsed before the first frame; the 340 MB of tiles were served uncompressed by `vite preview`; a request for a tile that had left the view could not be stopped; nothing said how a host should cache the files. Budgets (`VERIFICATION.md` 5): initial payload <= 3 MB, JS <= 600 KB gzip, first render <= 3 s.
- **Decision:**
  1. **Manifest format 2: a small root and shards.** `tiles.json` keeps the header, attribution, layers, `levels` (level, block, tolerance, unit, keeps, totals; no tile list), the `index` and `minimap` entries, `totals`, and gains `bounds_local` (ground extent of the base tiles, for the camera) and `shards`: one record per shard file (level, id, `shards/S<level>_<a>_<b>.json`, bytes, gzip-9 bytes, sha256, tile count, union of the content boxes). A shard is a literal slice of the old manifest: the same tile entries, sorted by id, one level, the tiles whose cell centre lies in one square of 8 x block of that level (2 km at level 0, 4 km at level 1, 8 km at level 2, 16 km at level 3). `format_version` is 2 (the client refuses 1); the committed schema (`tiles.schema.json`) describes the root and, under `$defs.shard_file`, the shards, and is checked by pytest and the data tests; `manifest.join_manifest` / `load_full` rebuild the old full manifest exactly (tested: `load_full(pilot)` equals the T-6.2 `tiles.json` apart from `format_version`). City: root 29,240 B raw (9,331 gzip-9, 7,318 B brotli as served), 101 shards (68, 21, 8 and 4 per level; 2.37 MB raw in all; largest 39,618 B raw, 72 tiles). The client fetches the root, then for each frame the shards of the level in use whose content box meets the view (grown by one tile ring), nearest first; loaded shards stay in memory. The pilot's tile files are byte-identical to T-6.2 (102 of 102 `.glb`, `.json` and `.svg`); only `tiles.json` changes (it is now the root, plus `shards/`).
  2. **Cache rules: versioned URLs, not revalidation.** Every file the manifest names is requested as `<file>?v=<first 12 hex digits of its sha256>` (tiles, feature tables, shards, `index.json`, `minimap.svg`; hashes from the root and the shards). The URL changes with the content, so a cached copy is valid for ever: `Cache-Control: public, max-age=31536000, immutable`. The only files that are not content-addressed are `index.html` and the root `tiles.json`: `no-cache` (revalidated with the ETag, a 304 costs a few hundred bytes), and the client fetches `tiles.json` with `cache: 'no-cache'` so it is revalidated whatever the host sends. Vite names JS and CSS by content hash: `/assets/*` is immutable. Revalidating every tile (the alternative) would cost one request per tile on every visit (about 120 for the default view); the version query costs nothing and works on a host that ignores query strings. Tile files requested without `?v=` are `no-cache` in the local server.
  3. **Precompression.** `web/scripts/precompress.mjs` (Node `zlib` only) writes `x.br` (quality 11, window 2^24, generic mode) and `x.gz` (level 9, memLevel 9, MTIME 0, OS byte 255) next to every `.html .js .mjs .css .json .svg .glb .txt .xml .map .webmanifest` file of the directories it is given, when the copy is smaller; a variant that already decodes to the file is kept (so the 340 MB of city tiles are compressed once, in `web/public/tiles/<extent>`, and copied into `dist` by the build). Deterministic for one Node build: fixed parameters, no timestamps, no platform byte; tested (two copies give identical bytes, a second run changes nothing). The compressed bytes of the same input can differ between Node/zlib builds and CPU classes (Chromium's zlib fork), so `.br`/`.gz` are build output, never committed, and byte identity of them across machines is not claimed. City: 8,805 files, 337.3 MB raw, 81.4 MB brotli (24 %), 142.8 MB gzip (42 %); first run 13 min 38 s (single thread, quality 11). `npm run precompress` and `npm run build:prod` (build, then precompress).
  4. **Local server.** `web/scripts/serve.mjs` (`npm run serve`, Node built-ins, 127.0.0.1 only, default port 4174, `--port`, `--dir`, `--encodings br,gzip`): GET and HEAD, no path leaves the directory, `x.br` if `Accept-Encoding` accepts br (q > 0), else `x.gz`, else the file; `Content-Type` by extension (`model/gltf-binary` for `.glb`), `Content-Encoding`, `Vary: Accept-Encoding` wherever a compressed copy exists, a per-encoding ETag and 304, the cache headers of point 2. `public/_headers` (copied to the root of `dist`) states the same rules for hosts that read such a file: `/` and `/index.html` `no-cache`, `/assets/*` and `/tiles/*` immutable, `/tiles/:extent/tiles.json` `no-cache`, general first, specific last. A path-only file cannot see `?v=`, so there `/tiles/*` is immutable by path; the client always uses `?v=` and revalidates `tiles.json` itself. A test reads `_headers` and checks it against the server's rule for eight sample paths. **Hosts:** Netlify and Cloudflare Pages read `_headers` (documented, not tried: nothing is deployed); GitHub Pages does not (fixed short `max-age`) and, to be confirmed, serves gzip only, not our brotli files. Brotli matters (point 6 of the consequences); the `.br`/`.gz` files are for a host or reverse proxy that serves precompressed files (nginx `brotli_static`/`gzip_static`, Caddy `precompressed`).
  5. **Streaming: cancel what is not wanted.** `TileStreamer` gives every request an `AbortController`; each update aborts the in-flight requests whose tile is no longer wanted (it left the view, or another level replaced it). A cancelled tile is forgotten, not failed (no retry, no error, no notice), never reaches the scene (checked after the fetch and again after the decode; the loader fetches the glb and the feature table with the signal and parses the bytes with `parseAsync`), frees its slot at once, and is requested again if wanted later. The shard requests are cancelled the same way. Order: the tiles in view first, nearest to the view centre first, then the prefetch ring (one tile ring around the view), nearest first; at most 4 requests in flight across levels. The test hook reports `started`, `completed`, `cancelled`, `inScene` (tile groups in the scene, equal to `loaded`) and `unwantedInFlight` (always 0).
  6. **Cache limit.** `CACHE_LIMIT` stays 64 tiles (loaded tiles kept; the least recently visible not-wanted tile is evicted first; a wanted tile is never evicted, so a view that needs more than 64 still loads completely and memory rises above the limit instead of thrashing). Measured on the 27-step path at 1280x720 and 412x915: peak tiles in memory 64 (the limit is reached, never exceeded), peak tiles in view 41 and 57, peak requests in flight 4. It fits because the largest view seen (57 tiles at 412x915) is below it and a tile is at most 250 KB gzip; the memory over a 5-minute session is T-6.4.
- **Consequences (numbers: `reports/artifacts/T-6.3/measurements.md`):** the root manifest is 29 KB instead of 2.36 MB, and the first frame needs 7 KB of it (brotli). The JS bundle is 707,775 B raw, 183,174 B gzip-9, 150,328 B brotli-11 (budget 600 KB gzip). Initial payload of the default view (origin, 600 m, city) with brotli: 1.40 to 1.80 MB at 1280x720 and 2.48 to 2.57 MB at 412x915 when the last tile of the view had arrived; 2.56 MB and 3.15 MB when the prefetch ring has arrived too. With a gzip-only client: 2.27 to 2.62 MB and 4.44 to 4.63 MB (the mobile view is level 1, whose tiles are 2x bigger under gzip than under brotli): **the 3 MB budget needs brotli on a phone**, which is a requirement on the host. First render 0.54 to 0.99 s (all 12 runs) and view loaded 0.89 to 1.06 s with brotli at 40 Mbit/s, 20 ms (software GL, one warmed-up browser per run; in a cold browser an exploratory first page needed 3.1 s for the first render, and a timeline run showed the app's first state only at 2.7 s: the SwiftShader start, which the warm-up removes). Scripted path of 27 steps over the four levels, scrubbing at 150 ms per step: 24 of 393 and 25 of 361 tile requests cancelled (0.31 MB and 0.27 MB received and thrown away; 2.25 and 1.36 MB for a gzip-only client), none in the scene, no unwanted request in flight at any 10 ms sample. The tile files themselves are unchanged (the pilot is byte-identical to T-6.2); the city is deterministic over two builds (8,802 files, 0 differences, Windows only: Linux is CI's check). Tests that read `tiles.json` use `manifest.load_full`. Not covered: a deploy, real GPU frame rates (T-6.4), the real behaviour of GitHub Pages, Netlify and Cloudflare Pages.

## ADR-0040 - Coarse tiles draw as two meshes, and the level switch has a draw-call cap (T-6.5, amends ADR-0037 point 1; owner decision of 2026-11-20: both fixes)
- **Status:** Accepted, amended by ADR-0041 (level 0 merged too; the budget reads as settled views) and ADR-0042 (exact count, smallest step) (owner decision of 2026-11-20 for the two fixes; the cap value of 280 and the numbers below are the executor's measurements, to be confirmed by the gate review).
- **Context:** gate G6 blocker B1. Every tile drew one mesh per layer, plus a shadow pass for its buildings, so a coarse tile cost 4.3 calls (shadows off) to 5.4 (on), and the level-2 range (1,920 to 3,839 m at 1280 px) had never been measured settled. The settled-view sweep `web/scripts/sweep-city.mjs` (8 windows from 360x640 to 2560x1440, 11 widths from 300 to 4,000 m, 5 centres, rotation steps 0 and 1: 880 views, each measured once nothing is pending and the draw calls stopped changing) gave, on the unchanged client, 211 views over 300 draw calls (232 over 280); maxima per window 256, 266, 351, 457, 460, 501, 460 and 685 (`reports/artifacts/T-6.5/sweep_before.json`). It reproduces the reviewer's 386 (1280x720, origin, 3,830 m) and 396 (1920x1080, origin, 4,000 m) exactly.
- **Decision:**
  1. **One mesh for the flat layers of a coarse tile** (`web/src/style/coarse.ts`, called by the tile loader for levels 1 to 3). `landuse`, `green`, `water`, `road_areas`, `roads` and `rail` of a tile are concatenated into one mesh named `coarse`, in that fixed order; `buildings` stay a mesh of their own because they are the only shadow casters. A coarse tile is now at most 2 meshes plus the shadow pass (3 calls at levels 1 and 2, 2 at level 3), where it was up to 7. The vertices are the file's own quantised Int16 data, concatenated (no re-quantisation, tested vertex by vertex); the node transforms of the layers must be equal, else the tile is drawn layer by layer as before. Same look: the lookup texture of the merged mesh holds, per feature, the palette index the separate layer used (flat layers: their single palette colour), indexed by `layer offset + feature id`; all lookup materials share the palette uniform, so day and night switch as before; the highlight mask has the same layout; the water sheen is applied by id range in the merged program (one new program, `milano-iso-feature-colour-merged-v1`; the programs of level 0 are untouched, so the visual baselines are unchanged). Picking: `userData.parts` maps an id range to its layer, so a hit returns the same layer and row (the same feature key) as before (vitest, and 45 hover points per view on real data, before and after, identical). Layer toggles: the triangles of the two toggle groups (water, green, land use; roads, road areas, rail) are contiguous in the index and a toggle sets the draw range. Shadow casting stays buildings only. Level 0 is not merged and no file changed.
     - **Why in the client and not in the pipeline** (measured on 98 real coarse tiles, `reports/artifacts/T-6.5/merge_cost.txt`): the merge costs 0.25, 0.61 and 0.98 ms per tile at levels 1, 2 and 3 (Node, against 1.0, 3.6 and 1.7 ms to parse the glb); meshes per tile 4.65, 5.30 and 4.39 become 1.98, 1.95 and 1.94; geometry bytes per tile 48, 171 and 207 KB become 46, 166 and 201 KB (the padding of the 6-byte position stream to 8 bytes is gone); textures per tile (a lookup and a mask per lookup material) fall from up to 10 to 4. Tile files, hashes and payload bytes stay as they were. Doing it in the pipeline would change every coarse glb (a new city build, new canonical hashes, and a new determinism surface under the CLAUDE.md lesson) to save under 1 ms per tile. No tile of the measured sample was left unmerged.
  2. **A draw-call cap on the level switch (amends ADR-0037 point 1).** The level of the 1-pixel rule (`baseLevel`) is chosen as before. Then `chooseBudgetLevel` (`web/src/tiles/levels.ts`) takes the next coarser level while the plan of the level is over `DRAW_CALL_CAP` = 280 calls, never above level 3 (`BUDGET_MAX_LEVEL`). The plan is the `planDraw` result for the tiles of the level that three.js will draw (the tile's bounding sphere meets the view, which is the test three.js applies per mesh), counted in the calls it will issue: `tileCalls` of each tile from its manifest `counts` (a base tile: one per layer present; a coarse tile: its buildings, plus one for the merged flat mesh), plus the shadow pass of each tile with buildings, counted over the view and its ring of prefetch tiles (the sun's shadow frustum is the bounding box of the rotated view footprint, so it reaches past the view), and only at the levels that cast shadows (below `NO_SHADOW_FROM_LEVEL`, and not with `?shadows=0`). The count assumes every layer shown, so it does not depend on the layer toggles. A level whose tiles in view are not all known yet (its shards are still on the way) has no plan: the coarser level in use stays, else the level is taken, and the question is asked again when the shards arrive, before any tile of it is requested. Hysteresis (`BUDGET_HYSTERESIS` = 0.9): a level left for the budget comes back only when its plan is at most 0.9 x the cap (252 calls), so a view hovering near the cap does not flicker. The state exposes `baseLevel`, `budgetSwitched` and `estimatedCalls` (test hook and sweep).
     - **Why 280:** over the 880 sweep views the plan was never more than 2 calls under the calls the frame issued (minimum -2, maximum +102, mean +12; the ground plane and the like), so 280 leaves 18 calls under the 300 budget for what the plan does not know (a chunked layer, a coarser tile kept while finer ones load). A higher cap gains little: the same views switch.
     - **Worst error the switch allows, measured:** on the 32 views of the sweep where it fired, the error of the level drawn (its tolerance over the metres per pixel) is at most **1.20 px**: 20 views at 2560x1440 from level 1 to 2 at 3,600 and 3,830 m (1.07 and 1.00 px), 10 at 2560x1440 from level 0 to 1 at 1,200 m (1.07 px), and 2 at 1440x900 from level 0 to 1 at 600 m, origin (1.20 px; there the plan counted 286 and 282 against 204 and 202 real calls, so the switch was not needed: the shadow ring of the plan is conservative at level 0, where a ring of 250 m tiles is large against a 600 m view). No view went to level 3 by the budget, so the 2 px limit of the card is not approached. By construction a switch to the next level has an error of at most the ratio of the tolerances (level 1 over level 0: 2.5; level 2 over level 1: 3; level 3 over level 2: 2), reached only at the lowest metres per pixel of the base level; no sweep view comes near it. Windows wider than 2,560 CSS px were not swept.
     - **How often it is needed:** with the merge alone (no switch in that build) 29 views draw more than 300 calls and 30 more than 280, all at 2560x1440, and the plan is over the cap on 32 views (`sweep_fix1only.json`); with the merge and the cap the switch fires on 32 of 880 views (3.6 %), and no view draws more than 268 calls (`sweep_after.json`). With the cap and without the merge it would be needed on 232 views (the number over 280 in `sweep_before.json`): the merge is what makes it rare.
  3. **Not covered:** frames while tiles are loading (a coarser tile is kept under the finer ones until they are all there; the plan is that of the settled view). The city bench (`reports/artifacts/T-6.5/budgets.md`) runs through those.
- **Consequences:** sweep maxima per window 115, 143, 178, 222, 223, 245, 223 and 268 draw calls (360x640 to 2560x1440), against 256 to 685 before; the coarse look is unchanged (`reports/artifacts/T-6.5/look/`: 8 views before and after, at most 2 of 921,600 pixels differ per view); the claim "within 300" of ADR-0037 and R-6.4 now rests on `npm --prefix web run sweep:city`, not on the bench path alone. ADR-0037 point 1 stands, except that the level drawn may be coarser than the 1-pixel rule allows where the plan is over 280 calls, by at most the 1.20 px measured.

## ADR-0042 - The draw-call count is the frame's own once the tiles are loaded, and the switch takes the smallest step (T-6.6, amends ADR-0040 and ADR-0041; closes accepted risks R1 and R2 of the G6 third review)
- **Status:** Accepted by the executor's measurements, to be confirmed by review. It replaces the figures of ADR-0041 on how often the switch fires and on its error.
- **Context:** the plan of ADR-0040/0041 counted every merged mesh of every tile whose content sphere meets the frustum (a bound, plan minus real 1 / 21 / 133). It made the switch fire where the level would have fitted (R1: 1920x1200, level 0 dropped at about 880-940 m; R2: 3840x2160 at 4,000 m, level 1 to level 3 with 2.88 px).
- **Decision:**
  1. **The count** (`LodController`, `culling.ts` `meshBounds`/`countBounds`). For a tile of the level that is loaded, the count is taken from its meshes: each mesh whose world bounding sphere meets the camera frustum (three.js's own per-mesh test) is one call, and each caster (`userData.casts`) whose sphere meets the sun's shadow frustum is one more; the spheres are computed once per loaded tile. A tile not loaded yet counts as the manifest says (every layer of a tile whose content sphere meets the view), a bound that is never below what it will cost. Only the tiles in view and the prefetch ring are drawn and counted, so what a level costs does not depend on what is left in the cache. `NON_TILE_CALLS` is now 1 (the ground plane); the margin of 2 is gone, because the count of loaded tiles is the frame's own.
  2. **Unloaded tiles.** If a level is over the cap only through the bound on tiles not loaded yet, it is not given up: while its plan has at most 192 tiles (`PROBE_MAX_TILES`; the largest wanted set in the sweeps was 162) and its bound times 0.4 (`PROBE_RATIO`; the real count was at least 0.44 of the bound in T-6.5b) could still fit, its tiles are loaded to count them, and the level in use stays meanwhile. The decision is asked again when tiles arrive (`needsRecheck`, `LodState.waiting`), and only then; a still camera on a settled view does not change level. A level 0 left for the budget and later in the cache only partly is loaded again to be counted (the coarser level stays meanwhile): in a genuinely heavy band the finer tiles are loaded once, counted, and dropped again, then kept out by the existing hysteresis (taken again at 0.9 of the cap). Views that never settle (tiles failing for good) count a failed tile as nothing and stop waiting.
  3. **Smallest step.** `chooseBudgetLevel` already goes to the finest coarser level that fits; with the exact count it now does so on every probed view: 3840x2160 takes level 1 to 2 at 3,600 and 4,000 m and level 0 to 1 at 1,200 m, never two levels.
  4. The cap (280), the hysteresis (0.9) and the ADR-0037 tolerances are unchanged.
- **Measured** (`reports/artifacts/T-6.6/`: `sweep.md`, `sweep.json`, `switch_need.json`, `parts/`; software GL, built at 39cad67):
  - **Views:** 7,080 settled views: the T-6.5b dense sweep (11 windows, 520-1,320 m every 40 m plus 300, 600, 1,200-4,000 m, 5 centres, rotation steps 0 and 1, both orders: 6,600), R1 (1920x1200, 6 centres, rotation steps 0-3, 840-1,000 m every 20 m, both orders: 432) and R2 (3840x2160 at 1,200, 3,000, 3,600 and 4,000 m, 3 centres, steps 0 and 1, both orders: 48). 0 not settled, 0 over 300, **maximum 280 calls** (3440x1440).
  - **Count minus real:** 0 / 0 / 0 (min / median / max) on all 7,080 settled views; the count is below the real count on none (real = renderer.info and the raw GL draw count of a fresh frame, equal). It was plan minus real 1 / 21 / 133 before.
  - **R1 closed:** at 1920x1200 the switch fired on 0 of 432 views (840-1,000 m); level 0 costs at most 251 calls there.
  - **Switch fired, needed:** on 148 views (110 distinct), at 2560x1440 (64), 3440x1440 (48) and 3840x2160 (36), nowhere else. Measured again with the switch off (cap 280): 2560x1440 fired 64, needed 64; 3840x2160 fired 36, needed 36; 3440x1440 fired 48, needed 30 (the other 18 are in the hysteresis band, where a level left at over 280 comes back only at 252, 253 to 280 calls off; by design). On the windows narrower than 2,560 px the switch fired on none and the level of the 1-pixel rule never exceeded 280 (max 251). Before: 346 of 375 distinct switched views were not needed.
  - **Worst error on a switched view:** 2560x1440 1.19 px, 3440x1440 1.43 px, 3840x2160 1.60 px (1,200 m, level 1 from 0); ADR-0041 had 2.33 px and 2.88 px. All switches are one level: 2560x1440 44 level 0 to 1 and 20 level 1 to 2; 3440x1440 32 and 16; 3840x2160 12 and 24; none to level 3. 3840x2160 at 4,000 m: level 2, 1.44 px, 168-223 calls (level 1 really costs 351 calls at the origin).
- **Consequences:** the switch fires only where the level of the 1-pixel rule really exceeds the cap (or inside its hysteresis band). The cost is some extra tile loading in a heavy band (the finer level is loaded once to be counted). Transitional frames are not covered, as before (settled views only).
